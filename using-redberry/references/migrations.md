# 数据迁移

各模块提供根层 `migrations/`，项目统一发现、排序和执行。一次执行覆盖整个项目的所有待执行迁移；SQLite 与 PostgreSQL 使用同一个数据库事务提交或回滚，MySQL 按下文的隐式提交边界处理。

迁移可由 `serve` 启动流程或独立 `migrate` 子命令触发，二者复用相同实现；配置检查不迁移。命令参数见[CLI 约定](cli.md#业务项目可执行文件)，模块路径见[目录结构](structure.md#模块结构)。

模块按方言子目录提供 SQL，CLI 和运行时发现各子目录中的版本。扩展数据库可通过 `backend/migration.go` 的 `MigrationModule` 提供迁移执行器；执行器负责该数据库的锁、账本、脚本选择和失败恢复，不继承内置数据库的事务保证。

## 启动迁移时机

`serve` 按以下顺序启动：加载与合并配置 → 校验配置 → 执行必要的版本迁移 → HTTP 开始监听并提供服务。

迁移失败则启动失败，不开始对外监听。执行过程中可以先初始化数据库等迁移所需资源，但不能在迁移尚未完成时对外提供服务。SQLite 与 PostgreSQL 的本次全部待执行迁移使用同一个项目级数据库事务；MySQL 使用专用连接和中断标记，失败仍阻止服务启动。

`check` 只校验配置，不执行迁移。

## 迁移执行顺序

模块迁移按模块依赖关系排序，先执行依赖模块，再执行消费模块；每个模块内部按版本顺序执行必要迁移。

依赖关系存在环时直接报错，不猜测执行顺序。迁移编排使用已解析、已选定实现的模块依赖图，遵守同一目标只允许一个实现的约定；所有模块的待执行迁移按此顺序执行；事务与失败恢复遵循当前数据库的能力。

## 迁移事务与失败处理

SQLite 与 PostgreSQL 的一次迁移执行以整个项目为事务边界：将所有模块本次待执行的迁移和对应版本记录纳入同一个数据库事务。按依赖与版本顺序执行，全部成功后统一提交；任一步失败则整个事务回滚，启动失败，不保留本批次部分成功的结果。

本批次开始前已成功提交的历史迁移不受影响。下次启动依据回滚后的版本记录重新确定待执行迁移，不将已回滚的步骤视为完成。

迁移执行器统一持有事务，各模块的迁移必须使用该事务，不自行提交或另开独立事务。SQLite 与 PostgreSQL 的首版迁移应遵守可在统一数据库事务中执行的约束；事务外副作用不属于数据库回滚能力，不能作为已受原子性保证的迁移步骤。

SQLite调整唯一键等需要重建父表时，执行器按官方表重建流程，在专用连接事务外临时关闭外键，仍在项目级事务内执行迁移；提交前完整执行 `foreign_key_check`，有不完整引用则回滚。成功或失败后恢复连接原外键设置；恢复失败丢弃连接。不能仅延迟外键检查后删除父表，因为删除可能执行级联副作用。业务连接设置保持原样。

MySQL DDL 会隐式提交，不能承诺整批回滚，也不能用 BEGIN 包装伪造原子性。执行器使用同一专用连接的会话锁串行化整批执行；每个脚本执行前写入 `rp_migration_dirty`，完成脚本及账本写入后清理标记。任一步失败即停止启动，后续启动发现中断标记时拒绝自动重跑。恢复必须先核对实际 schema、脚本效果与账本，再按项目恢复流程处理，保留失败前可能已经提交的事实。

## 并发启动的迁移协调

同一数据库的整批迁移需要加锁。执行器先取得迁移锁，再读取版本记录、确定本批待执行迁移，再按数据库事务能力执行；锁覆盖版本读取至整批执行完成或失败收尾。

其他实例等待锁；取得锁后重新读取版本记录，不复用等待前的迁移计划，跳过前一个实例已提交的迁移。若前一个实例失败回滚，则根据当前数据库记录重新确定待执行步骤。

等待超时则启动失败，不绕过锁执行迁移，也不开始对外提供服务。锁作用于同一数据库的多个应用实例，不能只使用单进程内的互斥锁。SQLite 首版采用 `BEGIN IMMEDIATE`，在读取版本记录前取得写事务，复用数据库锁，不增加迁移锁表或独立文件锁。提交或回滚结束本次事务并释放锁；提交失败必须确保事务和连接状态得到清理。锁等待默认超时为 30 秒，允许配置覆盖；超时后启动失败，明确报告“等待迁移锁超时”。此值仅限制锁等待，不限制整批迁移的执行时长。

迁移连接单独应用立即写事务与锁等待设置，不将普通业务事务全部改为 IMMEDIATE。等待策略须作用于实际使用的连接，不能只在连接池任意连接上执行一次 PRAGMA。

## 迁移方向

首版只支持向前迁移，不提供自动降级或 `down` 命令。本批次执行失败时通过项目级事务整体回滚；这不等于撤销已成功提交的历史迁移。

已提交的历史变更通过新增迁移修正，不通过反向执行历史脚本撤销。服务版本回滚时保留数据库现状，直接运行，由实际运行结果判断是否可用。不增加迁移兼容性声明、最低兼容程序版本或基于数据库版本高低的启动拦截，不自动降级数据库。

数据库中存在当前程序不持有的新迁移记录，不因此报错；已执行的迁移不重复执行。正常配置校验、迁移执行错误和实际运行错误仍按各自规则处理。

## 替代模块的迁移归属

替代模块按自身模块 ID 独立记录和执行迁移，不继承、不映射原模块的迁移历史。内置执行器的 `rp_migrations.module` 使用实际执行迁移的模块 ID，不改写为被替代目标 ID。

安装选择确定后，只发现和执行当前参与装配模块的迁移。原模块留下的数据和迁移记录不自动清理，框架不额外处理原实现，也不建立迁移历史转换机制。

此规则仅确定迁移归属，不改变替代模块沿用目标配置组名和配置契约的约定。

## 表与字段备注

新增或调整数据库表时，为表、每个字段及关键索引／约束提供中文备注，说明业务用途、状态取值、单位、可空语义及安全含义；按实际字段语义填写，不只重复标识符。

支持原生备注的数据库使用对应的表／列 COMMENT 语法，使数据库工具可读取。SQLite 使用建表 SQL 内的中文注释：表说明放在 `CREATE TABLE` 的括号内，字段说明靠近列定义，关键索引／约束单独说明；同时在模块文档解释需要跨字段理解的规则。SQLite SQL 注释不等同于原生 COMMENT 元数据。

统一覆盖业务表、框架内部表及 CLI 生成模板。验收核对备注与实际 DDL 一致，并在干净数据库执行迁移。已发布或已执行且需保留的历史迁移遵守校验和规则，通过新迁移补充原生备注；SQLite 的历史说明可补在当前 schema 文档中。只有明确重建未发布首版并清空开发数据时，才合并或改写首版迁移。

## 迁移文件命名

```text
migrations/
├── embed.go
├── 0.1.0.sql
├── 0.2.0.sql
└── 1.0.0.sql
```

SQL 文件名直接对应模块版本，不带 `v`；每个版本最多一份 SQL。没有数据库变更的模块版本无需提供迁移文件，不要求每次发布都新增迁移。

根据迁移账本找出尚未执行的文件，在模块依赖顺序内按版本数值顺序执行，不按文件名的字典序排列。历史文件遵守已定的校验和与只向前迁移规则。

`pnpm check` 静态检查迁移文件：

- 迁移文件版本不得高于所属模块 `redberry.yaml` 的 `version`。
- 同一模块不得出现重复迁移版本。
- 迁移 SQL 文件名必须是合法版本名，遵循不带 `v` 的命名约定。

检查失败直接报错，不跳过异常文件或自动修正版本。重复版本按解析后的版本身份判断，不依赖文件路径字符串是否相同。

## 迁移记录表

内置执行器维护 `rp_migrations`，记录模块 ID、迁移版本、校验和及执行时间。各模块只提供迁移内容，不各自维护迁移进度表；SQLite 与 PostgreSQL 的记录与本批次业务变更使用同一项目级事务；MySQL 同时维护中断标记并遵守 DDL 隐式提交边界。扩展执行器负责自身数据库的迁移账本、锁与恢复。

框架内部表统一使用短前缀 `rp_`，表名沿用 snake_case 与复数风格。字段确定如下：

| 字段 | 含义 |
| --- | --- |
| `module` | 模块 ID |
| `version` | 迁移版本 |
| `checksum` | 已执行迁移文件的校验和 |
| `migrated_at` | 迁移执行记录时间，沿用 Bun 命名 |

以 `(module, version)` 为联合主键，不额外增加自增 ID，也不增加 `group_id`。记录随整批迁移一起提交；`checksum` 使用 SHA-256，对迁移文件原始字节计算，保存为 64 位小写十六进制字符串，不做换行、空白或 SQL 内容归一化。

## 历史迁移校验和

记录已执行迁移文件的校验和，当前程序持有的已执行历史文件内容发生变化时直接报错，需要修正时新增迁移。校验和统一使用文件原始字节的 SHA-256，以 64 位小写十六进制字符串保存；任何字节变化均产生不同校验结果，不进行内容归一化。

旧程序不持有的新迁移文件不因缺失而被判为篡改；服务回滚是否可用由实际运行结果判断，不另行做结构兼容性预判。
