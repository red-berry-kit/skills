# 设计与架构

## 项目定位

红梅（Red Plum）是一套面向 Agent 辅助编程的 Go 业务项目模板。它提供可组合的基础能力、统一约定和静态检查边界，让开发集中于业务功能。

项目包含后端、前端、skill / tool 三部分，独立处理、按需加入。当前 Agent 开发的重点是编程过程中的约束，让开发者和 Agent 从类型、约定与检查结果中获得明确反馈。Agent 文档入口、工具职责和任务流程见下述设计；交付状态见[实现范围](status.md)。

项目共用一套结构，业务模块按需添加。具体业务模块分别设计，不预先固定全部功能。

## 设计原则

| 原则 | 约定 |
| --- | --- |
| 约定优于配置 | 约定路径、入口和资源位置，避免模块重复声明 |
| 清晰且简短 | 兼顾语义和链路一致性，在此前提下简化命名 |
| 模块独立、按需组合 | 用户业务也是独立模块，前端、后端及资源按需提供 |
| 基础集中维护 | 基础模块与公共工具统一维护，使用方按版本升级 |
| 静态边界明确 | 类型和现成规则能检查的约束交给工具 |
| 减少定制 | 优先依赖原生能力与标准格式，缺口才补小范围适配 |
| 先验证再决定 | 关键选型通过实际接入验证，保留能力限制 |

## 模块如何组合

每个模块拥有独立的身份、版本、依赖和公开入口。后端通过 Fx 组合构造器与生命周期；前端通过静态可见的入口和完整路由树保留类型关联。

CLI 管理源码、版本、工作区和装配输入，依赖注入负责对象和资源的组合。两者共用模块图，不让业务分别维护脱节的安装与装配步骤。

自有模块放项目内的模块目录，外部源码放 Git 忽略的 `.redplum/modules/`。项目提交 YAML 清单和锁文件，以便团队与 CI 恢复依赖。自定义行为留在业务模块或独立实现中，外部目录不作为长期修改基础源码的地方。

替代实现通过 `replaces` 声明目标模块 ID 与大版本，消费方继续依赖目标约定。同一目标只允许一个实现，选择后全项目生效；替代维护者负责遵守约定，框架执行正常编译与边界检查，不另建健全性评估机制。详见[模块与依赖](modules.md)。

## 业务开发链路

```text
模块源码与依赖清单
    → CLI 安装、解析与装配
    → Fx 后端 / 前端入口与路由
    → 业务接口与 TSX 页面
    → 统一检查、测试与构建
```

API 以 Go 类型及接口注册为来源，经 Huma 生成 OpenAPI，再由 Orval 生成类型、Fetch 调用与 Query 接入。前端各部署形式统一使用 `/api` 相对路径，不手改生成代码。

成功响应使用业务结构，失败沿用 Huma ErrorModel。列表使用 `page`、`size`，以服务端返回的实际分页值为准；常规编辑采用完整 PUT，区分必填、可空与零值。ID、时间日期和错误状态遵循统一[API 契约](api.md)。

前端使用 React / TSX 与 Mantine 的有限公共入口。主题、布局语义和静态边界约束风格；Router、Query、Form、Table 分别承担自己的状态职责，日期与错误处理沿用现有组件能力，见[前端开发](frontend.md)。

强校验针对代码、类型、规范和模块边界，不要求客户端重复执行请求、响应 Schema 校验。服务端输入校验与表单业务校验保留各自职责。

## 配置与迁移

模块用 Go 类型声明配置，项目统一生成编辑 Schema、合并公共与环境配置、校验后注入。配置在启动时固定，构建不携带部署配置；HTTP 与配置共用 Huma 校验体系，见[配置](config.md)。

迁移资源属于模块，执行批次属于项目：所有本次待执行迁移及版本记录在一个事务中统一提交或回滚。并发启动先取得数据库迁移锁，再读取版本与执行；该事务范围不扩展到普通业务操作，见[数据迁移](migrations.md)。

## 工程入口与交付

### Agent 文档入口

项目根 `AGENTS.md` 是 Agent 开发的统一入口，由 `redplum create app` 初次生成，简要说明项目结构、常用 `redplum` 与 `task` 命令、用户模块和 `.redplum/` 生成目录的边界，并留出项目特有规则区。可提示使用用户已安装的 Red Plum Skill，不绑定客户端路径；不复制完整规范。创建后由业务项目维护，后续 CLI 操作、Skill 或官方规范更新均不覆盖。

具体任务按需提供 Skill，以 `SKILL.md` 描述任务流程，并按需配套脚本和参考资料。官方 Skill 发布包携带该 Skill 实际需要的规范资料，放在 Skill 目录的 `references/` 下并使用包内相对路径；参考资料由本仓库 `docs/` 生成，同 Skill 使用相同版本。用户自行获取、安装和更新 Skill 包，安装位置遵循所用客户端的约定。

公开文档站提供 `llms.txt`，作为面向 AI 的文档索引，从文档结构生成并链接详细内容。它承担网站资料导航；项目开发规则由 `AGENTS.md` 承载，任务流程由 Skill 承载。具体自动发现与加载行为取决于所用 Agent 客户端。

### 开发工具入口

Red Plum CLI 负责从项目模板和模块模板创建项目与模块，并维护项目声明的模块依赖；CLI 将输入填入模板，再执行必要的依赖接入。项目根 `Taskfile.yml` 提供 Agent 和开发者统一使用的任务入口，组织生成、检查、测试、开发和构建；这些任务调用 Red Plum CLI、编译器、静态检查器及测试工具完成具体工作。CLI 的 `gen`、`check` 是 Task 调用的底层命令，不另设一套项目级任务编排。

Skill 说明何时使用 CLI 或 Task、如何判断结果并继续工作，不重复实现命令能力。业务运行时供 Agent 调用的工具按业务模块需要单独设计，不预设通用工具集合或统一注册层。

### 编码 Skill

编码 Skill 贯穿需求理解、调研、架构与方案设计、技术选型及 POC、编码、检查测试、文档与交付。创建模块、开发接口、开发页面先作为开发入口的专项参考流程，共用通用规范；存在独立触发或复用需求时再拆成 Skill。

| 环节 | 要求 |
| --- | --- |
| 需求理解与调研 | 阅读现有实现和规范，明确目标、边界与验收条件；调研官方资料和社区实践，优先复用已有能力 |
| 架构设计 | 明确模块职责、依赖方向、公开接口、数据流与生命周期，遵守项目现有架构 |
| 设计模式与抽象 | 根据具体问题选择模式，评估其收益与复杂度；根据实际变化点建立抽象，优先简单直接的实现 |
| 选型与 POC | 综合维护状态、生态、项目适配度、可读性、可测试性及 Agent 修改边界评估；形成初步设计或选型结果后，需要实战验证才能定案的方案通过真实接入的 POC 验证 |
| 命名与编码 | 遵守统一的文件、标识符、API 字段命名和前后端代码风格，复用专题规范 |
| 检查与测试 | 执行格式、静态检查及适合本次变更的测试；涉及调用链路时验证真实接入 |
| 文档与交付 | 同步最终方案文档，依据实际执行结果报告完成情况，明确未验证范围 |

流程按任务规模裁剪。小修改沿用现有设计；涉及模块边界、新依赖或架构变化时，展开对应设计与验证，避免为假设需求预留扩展。

格式及可静态检查的规则由工具执行，Skill 负责指导判断、组织流程并要求运行相应检查。专项流程复用既有 CLI 与 Task，不重复实现执行工具；详细规则在专题文档中统一维护。

### Skill 组织方式

遵循 [mattpocock/skills](https://github.com/mattpocock/skills) 的小型、独立、可组合方式组织。完整编码流程由一组职责明确的 Skill 协作完成，工作流入口组织任务，共享 Skill 提供编码规范、架构设计、调研、POC 和验证等可复用指引。

- Skill 源码直接位于 `skills/<skill-name>/`，不增加分类目录；目录名与 Skill 名一致。
- 整套 Skill 的入口名为 `using-redplum`；其他 Skill 使用 `redplum-` 前缀，职责使用完整英文单词。目录名与 `SKILL.md` 的 `name` 一致；CLI 命令仍沿用简短命名。
- 每个 Skill 使用 `SKILL.md`，YAML 元数据中的 `description` 用英文说明职责与触发条件，正文用中文。
- 所有相关任务都需要的步骤与约束放在入口；仅部分任务需要的详细说明放在同目录的辅助文档中，并注明读取条件。已有专题规范直接引用。
- 只有存在独立触发场景或复用需求时才拆成新 Skill；单纯的补充说明保留为普通参考文件。
- 区分用户主动启动的工作流与 Agent 按任务选用的共享能力；具体发现路径、调用机制及元数据适配以目标客户端为准。
- Skill 源码组织与业务项目安装位置分别定义；源码目录不代表各客户端会自动发现其中的 Skill。
- 编写与修订配合 `writing-skills`、`skill-creator` 和 `writing-for-agents`：先建立无 Skill 的行为对照，再根据实际问题编写或修正，逐项验证后继续下一项；同时检查触发条件、完成条件、内容层次与文件结构。对照未暴露的问题不作为追加约束的依据。

### Agent 资源维护

| 资源 | 维护与更新方式 |
| --- | --- |
| 官方 Skill 与配套规范 | 正式规范在 `docs/` 单点维护；发布时为各 Skill 生成所需的 `references/`，与 Skill 同版本发布；用户自行获取、安装和更新 |
| 项目根 `AGENTS.md` | 创建项目时生成，由业务项目维护，保留开发入口和项目特有规则 |
| 用户自建 Skill 与补充规范 | 由业务项目维护，官方更新不覆盖 |

Skill 和配套规范不放入 `.redplum/`，不纳入 Red Plum CLI 的安装、恢复、更新或依赖管理。Skill 包内的 `references/` 必须包含它实际引用的规范，使单个 Skill 可独立读取且无需联网；正式文档仍只在 `docs/` 维护，发布副本由其生成。用户自行选择所用版本和安装方式，官方不覆盖项目自定义内容。

### Skill 职责划分

| 名称 | 职责 |
| --- | --- |
| `using-redplum` | 整套 Skill 的使用入口，理解任务、选择并串联所需 Skill，组织实施与交付 |
| `redplum-research` | 调研需求相关的已有实现、官方资料及社区实践，记录来源与结论 |
| `redplum-design` | 架构、模块边界、接口、依赖方向、抽象与设计模式选择 |
| `redplum-proof-of-concept` | 对初步设计或选型结果进行实战验证，提供可复现结果并支持最终定案 |
| `redplum-coding` | 编码纪律、命名与代码风格、测试策略及检查测试执行要求 |
| `redplum-code-review` | 审查需求符合度、设计合理性、代码规范及验证证据 |
| `redplum-debugging` | 复现问题、收集证据、定位根因、修复及回归验证 |

重构由设计与编码能力协作完成，并验证既有行为；文档维护贯穿开发流程，交付前同步最终方案；依赖升级组合调研、必要的 POC、编码与验证。上述任务复用现有 Skill，不单独拆分。

### 使用入口流程

`using-redplum` 保持简短，负责流程选择与组织，专业规则由对应 Skill 维护。

1. 理解任务：读取项目规则与相关实现，明确目标、边界及验收条件；仅询问会影响结果且无法自行查明的问题。
2. 判断路径：小修改直接编码；新需求先做针对性调研；涉及模块边界或架构变化时进行设计；已有初步设计或选型结果、需要实战定案时进行 POC；故障修复进入排障流程。
3. 组织实施：按可验证的小步推进，遵循编码规范，复用项目 CLI、Task 和现有实现。
4. 验证交付：运行对应检查与测试，结合变更范围进行代码审查，同步文档，报告实际结果及未验证范围。

每一步具有明确产出，不要求每一步新增文件。已有结论直接复用；调研与实验记录进入过程资料区，最终有效规则进入方案文档。

入口按任务选择以下能力，一次任务可组合多项，并按实际依赖顺序执行：

| 任务情况 | 使用的 Skill |
| --- | --- |
| 编写或修改业务代码 | `redplum-coding` |
| 新需求、需要核实技术事实或寻找现成方案 | `redplum-research` |
| 调整模块职责、接口、依赖方向、抽象或设计模式 | `redplum-design` |
| 已有初步设计或选型结果，需要通过实战验证定案 | `redplum-proof-of-concept` |
| 报错、行为异常或性能问题 | `redplum-debugging` |
| 用户要求审查，或重要变更完成后 | `redplum-code-review` |

需要实战定案的任务依次进行调研、初步设计或选型、POC 实战验证、根据结果定案及正式实施。纯说明、简单查询或文档纠错直接处理，无需展开完整开发流程。

`using-redplum` 支持 Agent 按任务自动选用，其余 Skill 可由入口按需使用，也可由用户主动调用。具体发现与调用方式适配目标客户端；不支持 Skill 间调用时，按需读取对应 `SKILL.md` 执行，不依赖某个客户端独有的工具。

### 调研流程

`redplum-research` 为需求分析、设计与选型提供有来源的结论，不代替真实接入验证。

1. 明确问题：结合需求与验收条件，确定需要查明的事实、限制及决策标准。
2. 阅读项目：检查已有实现、已定方案及相关实验，复用仍适用的结论。
3. 查证资料：需要外部资料时，优先官方文档、源码、发布记录及维护状态，再结合社区实践判断实际使用情况。库与工具的行为按项目目标版本核实。
4. 综合判断：结合现有技术栈、维护成本、静态检查能力与 Agent 开发边界评估方案，区分来源事实、项目推断和待验证假设。
5. 交付结论：给出推荐方案、适用条件、限制、来源及待验证问题，作为设计或 POC 的输入。

问题已有充分依据、足以支持当前决策时结束调研。形成初步设计或选型结果后，需要通过实战验证才能定案时进入 POC；尚未查清的事实继续调研。选型调研检查维护活跃度及社区采用情况，不仅依据版本号高低、仓库星数或宣传判断。

POC 开始前明确候选方案与验收条件，完成真实接入后依据结果定案；结果不满足要求时调整方案并继续验证。

简单事实查询可直接回复并附来源；需要复用的调研结论保存在项目已有过程资料区。最终确认的有效规则同步到专题方案文档，保留验证范围与实现状态的区别。

### 设计流程

`redplum-design` 根据任务规模确定设计深度，优先沿用项目现有架构。设计模式用于解决具体问题，不要求每个功能都套用模式。

1. 明确设计输入：需求、验收条件、现有架构与调研结论。
2. 确定职责与边界：明确各模块负责的内容、协作接口及依赖方向。
3. 设计关键行为：明确数据流、生命周期、错误处理及必要的事务边界。
4. 选择实现方式：优先简单直接的方案；采用抽象或设计模式时，说明其解决的实际问题及维护成本。
5. 形成初步方案：明确变更范围、接口、验证条件与适用限制。需要实战定案时交由 POC 验证，再根据结果完善设计。

沿用既有架构的小修改无需额外产出设计文档。需要文档时，已定规则在对应专题中维护，调研比较与实验材料进入过程资料区。

### POC 流程

`redplum-proof-of-concept` 以初步设计或选型结果及验收条件为输入，通过实战验证支持最终定案。

1. 明确输入：候选方案、目标技术栈与版本、实际使用场景、验收条件及验证范围。
2. 完成真实接入：在目标技术栈中接入候选方案，验证关键行为与完整调用链路，不能仅凭孤立示例判定融合可行。
3. 执行验证：运行相关编译、类型与静态检查及场景测试，依据实际结果判断是否满足验收条件。
4. 保留证据：在过程资料区保存复现步骤、必要代码、执行结果与适用限制，区分已验证和未验证范围。
5. 支持定案：通过后根据证据确定方案；未通过时分析原因，调整方案并继续验证，不降低既定检查标准。

实验通过不代表正式模板、CLI 或公共组件已经交付。最终确认的规则同步到专题方案文档，实验材料继续保留在过程资料区。

### 编码流程

`redplum-coding` 将任务要求与已定方案落实为代码，复用项目已有规范、实现及检查入口。

1. 读取规范：根据变更范围阅读相关专题及邻近实现，确认文件位置、命名、公开入口、依赖边界和代码风格。
2. 小步实施：按可验证的步骤编码，沿用现有实现方式；需要调整设计或选型时回到对应流程。
3. 检查代码：通过项目统一入口执行相关格式检查、静态检查、编译及独立类型检查，修复发现的问题。
4. 验证行为：根据需求、变更风险及影响范围选择必要测试；涉及前后端或持久化链路时验证真实接入，不以编译通过代替行为验证。
5. 准备交付：核对需求与验收条件，同步受影响文档，并提供实际检查测试结果及未验证范围，供后续审查与交付使用。

文件、标识符和 API 字段遵循对应语言及项目既有命名约定。业务不自行关闭既定规则，不手改生成代码绕过检查；修复应落在实际问题所在的源码、生成输入或配置中。

### 代码审查流程

`redplum-code-review` 围绕需求符合度、设计合理性、代码规范和验证证据审查变更，以需求、已定方案、项目规范及实际代码行为为依据。

1. 确认范围：明确本次变更、需求与验收条件，阅读受影响实现及相关规范。
2. 核对需求与设计：检查业务行为、模块职责、接口、依赖方向及必要的边界处理是否符合要求。
3. 核对代码规范：检查命名、代码风格、公开入口、生成代码边界及项目约束，复用工具已有检查结果。
4. 核对验证证据：检查实际执行结果与变更范围是否匹配，明确遗漏的验证场景和未验证范围。
5. 报告与复查：问题附具体位置、影响与依据，区分必须修复的问题和可选建议；修复后复查相关部分。

个人偏好不作为项目规则。没有发现问题时如实说明，并保留验证范围的限制，不将审查结论扩大为全面正确性保证。

### 排障流程

`redplum-debugging` 先建立问题证据，再定位根因并修复。

1. 明确现象：记录预期与实际行为、触发步骤、相关环境及影响范围。
2. 复现与取证：建立可重复的复现方式，收集必要的日志、错误、输入输出及执行条件；无法复现时明确缺少的条件，继续补充证据。
3. 验证假设：依据证据提出根因假设，通过有针对性的检查或实验验证，避免同时修改多个无关因素。
4. 针对性修复：定位后修复实际原因，遵循编码规范，避免凭猜测修改代码或顺带进行无关重构。
5. 回归与交付：确认原问题得到解决，补充必要的回归验证，执行受影响范围的检查，并报告根因、修复及实际验证结果。
