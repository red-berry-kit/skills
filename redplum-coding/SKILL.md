# 红梅编码

将已定需求与方案落实为可验证的代码。以目标项目规范、现有实现和实际工具入口为准；红梅源码仓库的规则入口是[开发约定](references/conventions.md)。

## 工作步骤

1. 确认契约与范围。阅读相关实现和验收条件，确定需要修改的源码、公开入口及生成输入。跨模块修改查阅[模块与依赖](references/modules.md)，接口修改查阅[API 契约](references/api.md)，页面修改查阅[前端开发](references/frontend.md)。
2. 小步编码。沿用语言惯例、邻近命名及项目约定，按可验证步骤完成业务实现。通过公开能力和显式依赖协作；需要超出已定方案的接口或架构变化时，回到对应设计步骤。
3. 更新产物。生成代码的修复落在源码、生成输入或官方配置中，再执行现有生成入口并核对差异。保持既定协议、模块边界及检查规则。
4. 检查与验证。从实际任务定义、脚本或工具帮助中选择可用命令，执行项目要求的格式、静态、编译及独立类型检查。按需求、风险与影响范围选择测试，验证可观察的行为和边界；涉及前后端或持久化时验证真实调用及最终状态。
5. 核对交付。逐项对应验收条件，检查实际差异及验证结果。必需检查或验收尚未完成时说明未完成项；已运行的部分成功不替代失败项或未执行项。

## 风格与验证边界

命名、字段和代码风格在对应专题维护，格式与可静态检查的约束交给工具执行。Vite 构建与测试不代替独立类型检查；检查命令和测试分层按目标项目现状选择，源码仓库的约定见[CLI 与开发流程](references/cli.md)及[技术选型](references/stack.md)。

遵守项目必需检查，其余验证按变更选择。低风险文案或等价局部修改核对差异及适当的现有检查，无需新增镜像实现的测试或扩大成架构任务。

交付说明实际改动、执行命令及结果，区分已验证、未验证与未完成。同步受影响文档中的最终规则，过程与实验结果留在项目已有记录区；只提出安排时明确尚未实施。
