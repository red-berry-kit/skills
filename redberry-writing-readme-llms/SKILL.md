# 模块 README.LLMS.md 编写

在 `README.LLMS.md` 编写本模块的使用约定，附相关公共入口短注与代码链接，按使用能力组织。

## 只写本模块

正文只写使用本模块的规则与公共入口：

- 与其他模块配合时，写调用方必须提供的条件，不写对方的职责、能力、行为或装配。其他模块或应用层名称无法改写为调用方条件时，删除该内容。
- 应用入口、路由、运行环境、偏好作用域与部署留在应用及其 `AGENTS.md`。
- 框架通用流程、跨模块原则与技术选型沿用原有来源，不在此复述。
- 删除实现原理、内部机制、未提供能力清单及源码目录组织。

## 内容归属

- `README.md`：模块介绍。
- `README.LLMS.md`：怎么使用、必须遵守什么、调用哪些公共入口。
- 代码声明及详细注释：类型签名、参数、字段、配置项、命令项、默认值、边界处理及具体示例。
- `AGENTS.md`：源码维护与验证要求。

统一称呼使用模块的实际名称。

## 统一格式

一级标题固定为 `# <模块名> 使用规范`。正文按能力使用二级标题，每节依次包含：

- `## <使用能力>`：标题直接表达使用场景，不按包或文件分组。
- `约定：`：独立一行，空一行后用 `- ` 列出具体规则。
- `公共入口：`：独立一行，空一行后用 `- ` 列出入口，每条为名称链接、中文冒号和用途短注。

标题、标记和列表之间留一个空行。统一使用这两个标记，不替换成过渡句、公共方法等变体；场景限定写入具体规则。没有独立规则或入口的内容并入相关能力，不添加空章节；没有独立入口的节不补 `公共入口：`。入口指向实际声明文件，名称需要消歧时加包名。

## 编写

1. **核对来源。** 阅读现有使用规范、相关公开声明、代码注释及必要测试。每条规则须来自用户已确认约定或实际实现；仅列使用者需要显式调用或声明的入口，内部协议钩子留在代码。
2. **按能力写约定。** 按统一格式列出前提、调用方责任、必须使用的入口和禁止的旁路。写可执行语句，保留有条件责任的原条件；正文以规则为主，方法清单不替代规则。
3. **就近列公共入口。** 每条只放方法或类型名称、用途短注、指向实际声明文件的相对链接；同一能力的相关入口可合并。签名、结构体、逐项参数值、示例代码及内部钩子的执行过程留在代码中。
4. **把详细接法留给代码。** 注释足以指导使用时直接链接；缺失时在已授权源码范围补齐，保留实现行为。正文只给规则与链接，不靠扩写正文或仅跳转 README 代替补齐注释。

完成条件：每条规则有来源，每个入口有实际用途且就近链接可找到具体接法；按正文即可判断使用规则，无需了解实现过程；正文未包含其他模块或应用层的做法。

## 写法示意

每节按“使用能力 → 适用条件与调用方动作／边界 → 公共入口名称、用途短注与声明链接”组织。按实际契约保留失败处理和安全约束；签名、参数及具体示例留在代码注释，不假设模块提供某种接口。

已确认约定与当前实现有缺口时，简短标明受限场景并单独交付待办，措辞限于已保证的行为。

## 验证

- 逐节按“只写本模块”检查内容归属；介绍、原理、未提供能力清单、技术细节及其他模块／应用层做法按规则删除、移回所属位置或改写为调用方条件。
- 逐节核对“统一格式”的能力标题、标记及列表顺序；没有独立入口的节省略 `公共入口：`。
- 核对规则是否具体可检查、入口是否简短可达、规则是否符合实际行为；保留必要安全与失败约束，措辞限于已保证的行为。
- 文件统一命名 `README.LLMS.md`，随模块交付；改名时同步有效引用、模板与交付测试，历史证据保留原事实。
