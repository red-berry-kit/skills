# 设计与架构

## 项目定位

红莓（Red Berry）是一套面向 Agent 辅助编程的 Go 业务项目模板。它提供可组合的基础能力、统一约定和静态检查边界，让开发集中于业务功能。

项目包含后端、前端、skill / tool 三部分，独立处理、按需加入。当前 Agent 开发的重点是编程过程中的约束，让开发者和 Agent 从类型、约定与检查结果中获得明确反馈。Agent 文档入口、工具职责和任务流程见下述设计。

项目共用一套结构，业务模块按需添加。具体业务模块分别设计，不预先固定全部功能。

## 设计原则

| 原则 | 约定 |
| --- | --- |
| 约定优于配置 | 约定路径、入口和资源位置，避免模块重复声明 |
| 清晰且简短 | 兼顾语义和链路一致性，在此前提下简化命名 |
| 模块独立、按需组合 | 用户业务也是独立模块，前端、后端及资源按需提供 |
| 基础集中维护 | 基础模块与公共工具统一维护，使用方按版本升级 |
| 静态边界明确 | 类型和现成规则能检查的约束交给工具 |
| 减少定制 | 优先依赖原生能力与标准格式，缺口才补小范围适配 |
| 先验证再决定 | 关键选型通过实际接入验证，保留能力限制 |

## 模块如何组合

每个模块拥有独立的身份、版本、依赖和公开入口。后端通过 Fx 组合构造器与生命周期；前端通过静态可见的入口和完整路由树保留类型关联。

CLI 管理源码、版本、工作区和装配输入，依赖注入负责对象和资源的组合。两者共用模块图，不让业务分别维护脱节的安装与装配步骤。

自有模块放项目内的模块目录，外部源码放 Git 忽略的 `.redberry/modules/`。项目提交 YAML 清单和锁文件，以便团队与 CI 恢复依赖。自定义行为留在业务模块或独立实现中，外部目录不作为长期修改基础源码的地方。

替代实现通过 `replaces` 声明目标模块 ID 与大版本，消费方继续依赖目标约定。同一目标只允许一个实现，选择后全项目生效；替代维护者负责遵守约定，框架执行正常编译与边界检查，不另建健全性评估机制。

## 业务开发链路

```text
模块源码与依赖清单
    → CLI 安装、解析与装配
    → Fx 后端 / 前端入口与路由
    → 业务接口与 TSX 页面
    → 统一检查、测试与构建
```

API 以 Go 类型及接口注册为来源，经 Huma 生成 OpenAPI，再由 Orval 生成类型、Fetch 调用与 Query 接入。前端各部署形式统一使用 `/api` 相对路径，不手改生成代码。

前端使用 React / TSX，通过 ui 模块的公开入口组合界面。主题、布局语义和静态边界约束风格；Router、Query、Form、Table 分别承担自己的状态职责，日期与错误处理沿用现有组件能力，细则随 ui 模块的 `README.LLMS.md`。

强校验针对代码、类型、规范和模块边界，不要求客户端重复执行请求、响应 Schema 校验。服务端输入校验与表单业务校验保留各自职责。

## 工程入口与交付

### Agent 文档入口

`AGENTS.md` 维护源码修改约束与验证要求，`README.md` 介绍模块，`README.LLMS.md` 维护使用约定和公共入口简注；详细接法放在代码注释中。编写使用说明时使用 `redberry-writing-readme-llms`。这些文档归所属源码维护。

Skill 以 `SKILL.md` 描述任务流程，并按需配套脚本；通用开发原则集中在本仓库 `standards/`，以该目录本身为索引。模块的公开类型、调用示例、配置和交付说明不在 Skills 中复制，也不另设逐项跳转文档。

规范以 `standards/` 下的专题页组织，Skills 目录以 `README.md` 与各 `SKILL.md` 为入口，不实现自动加载。用户自行安装和更新 Skill 包；安装位置与自动发现行为取决于所用 Agent 客户端。

### 开发工具入口

Red Berry CLI 负责从项目模板和模块模板创建项目与模块，并维护项目声明的模块依赖；CLI 将输入填入模板，再执行必要的依赖接入。项目任务脚本提供统一的生成、检查、测试、开发和构建入口，具体命令以目标项目定义为准；任务调用 Red Berry CLI、编译器、静态检查器及测试工具完成工作。

Skill 说明何时使用 CLI 或项目任务入口、如何判断结果并继续工作，不重复实现命令能力。业务运行时供 Agent 调用的工具按业务模块需要单独设计，不预设通用工具集合或统一注册层。

### 编码 Skill

Red Berry Skills 的统一入口为 `using-redberry`。入口负责阶段选择、任务恢复和交付；每个专业 Skill 的执行步骤、出口和交接以其 `SKILL.md` 为唯一流程定义。本页只说明资源边界，不再复制流程表。

项目 `AGENTS.md` 应指向已安装的 `using-redberry`，由入口按任务选择专业能力。具体发现、读取或调用机制遵循所用客户端；源码目录不等于客户端安装目录。缺少某项 Skill 时应说明缺失并继续有依据的工作，不伪称已使用。

### Skill 组织与维护

- Skill 源码在独立 Skills 仓库根的 `<skill-name>/SKILL.md`；名称与目录一致，统一入口为 `using-redberry`，专业 Skill 使用 `redberry-` 前缀。
- `description` 用英文描述触发条件，正文与说明用中文。入口组织流程，专业 Skill 定义阶段要求，技术规范按需引用。
- 需求、计划与验收分别由 `redberry-requirements`、`redberry-planning`、`redberry-verification` 承担；调研、设计、POC、编码、排障和审查保持各自职责。新增 Skill 应有独立触发场景，补充说明可保留为参考文件。
- 跨模块规范在本 Skills 仓库的 `standards/` 单点维护，Skill 按需读取对应 URL；模块专属说明在所属模块维护，使用实际安装版本，不随 Skill 复制。无需技术规范的 Skill 保持自包含。
- 任务流程直接修改对应 `SKILL.md`，不在规范副本重写；新增或修订流程先建立行为对照，再验证阶段选择、产出与交接，检查实际行为，不能只匹配标题。
- 项目 `AGENTS.md` 保留维护流程入口及项目特有修改约束，`README.LLMS.md` 维护使用入口，均由项目维护。用户独立安装和更新 Skills，Red Berry CLI 不管理、不覆盖它们，`.redberry/` 不保存 Skills。
- 源码更新不等于所有客户端已加载；安装后核对实际路径，发现目录可能需要客户端重新扫描。未安装的下游 Skill 不能作为已执行的证据。

### 任务与发布

项目通过已有任务入口统一生成、检查、测试、开发和构建，不以局部 POC 代替正式交付。

技术选型见[技术选型](stack.md)，日常规则索引见[开发约定](conventions.md)。
