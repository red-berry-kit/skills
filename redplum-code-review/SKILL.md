# 红梅代码审查

以需求、已定方案、项目规范和实际行为为依据审查变更。目标项目规则优先；红梅源码仓库的流程见[代码审查流程](../../docs/design.md#代码审查流程)，规则入口见[开发约定](../../docs/conventions.md)。

## 工作步骤

1. 确认范围。固定审查基点与当前变更，包含新增文件，读取相关需求、验收条件及受影响的上下文。
2. 核对行为与设计。追踪关键输入、调用及结果，检查需求、不变量、错误处理、模块职责和依赖方向。依据实际代码区分独立问题，尚未查明的行为作为待核实项。
3. 核对项目规范。检查公开入口、命名风格、生成代码边界及相关约束；复用现有工具结果，个人偏好与项目要求分开。
4. 核对验证证据。将实际执行的检查测试对应到变更及验收条件，识别遗漏场景、失败和未执行项。有必要且可执行时做针对性检查，报告实际范围。
5. 给出结论并复查。按影响排序报告问题，区分必须修复与可选建议。仅审查的任务保持审查范围；已授权修复时处理问题，再复查相关变更及验证结果。

## 问题报告

每项实质问题包含：具体文件位置、触发条件与影响、代码或规范依据，以及针对性的修复或复查建议。结论应足以让维护者定位并评估问题，不把尚无依据的猜测当成缺陷。

没有发现问题时如实说明审查范围及验证限制。检查通过或未发现问题不等于全面正确性保证；已有部分测试通过也不代表需求完整验证。
