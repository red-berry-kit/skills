# 开发约定

本页是日常开发的规则索引。字段、参数和目录的完整定义以所链接专题为准。

## 设计与命名

- 约定优于配置：通过固定路径发现入口和资源，不在每个模块重复声明。
- 命名兼顾语义与链路一致性，在此前提下使用清晰短名，不为对齐单个库破坏整体约定。
- 优先复用依赖原生能力、标准格式与社区约定，缺口才补小范围适配。
- 用户业务与基础能力都是独立模块，前端、后端和迁移按需加入。

### 命名判据

名称从使用场景与目的出发：界面以用户要完成的操作命名，代码与配置以调用方关心的业务含义或职责命名，不从实现步骤、组件名或为了显得完整而堆词。优先使用清晰、直观的最短充分表达，简洁以不丢失语义和作用范围为边界。公开名称应让调用方看出它控制的规则或承担的职责。设计时用一个实际调用或配置示例检验，编码时贯通调用链，审查时指出具体歧义及影响。

- 同一概念沿配置、接口、代码和文档统一用词，优先沿用项目已有领域术语。
- 名称区分规则与状态。表示集合包含、排除的规则可用 `include` / `exclude`；时间区间、数值上下界、分页等按各自领域含义命名。
- 利用界面上下文省去已明确的对象。例如“记录列表”内的操作按钮用“新增”，英文用“Add”，不重复写“新增记录”／“Add record”。只有多个对象或脱离上下文会产生歧义时，才补充真实领域对象；不机械删掉所有名词。
- 判断名称时用实际页面、调用或配置检验：能否立即理解目的、是否重复上下文、是否混入实现术语、是否省略了必要差异。只评价字数或孤立词形不能代替场景判断；纯图标的可访问名称、危险操作确认等仍须表达清楚操作和必要对象。
- 利用模块和类型上下文省去重复限定词，保留决定行为差异的词。集合、布尔值和动作遵循语言惯例；后缀或缩写以消除实际歧义为依据。
- 示例能说明名称的用途、作用范围和易混概念的区别才算检查完成；检查发现语义不符时调整名称或职责。仅词形偏好列为可选建议。

定位与职责见[设计与架构](design.md)。

## 独立应用边界

同一宿主交付多个应用时，每个应用独立拥有入口、路由、静态资源和处理链。构建产物与嵌入资源按应用或资源类型分目录，应用名、资源索引和目录名一致；共享进程或二进制不改变所有权。应用不得读取或暴露其他应用的资源，也不得依赖其他应用的挂载路径。

多应用交付采用统一的应用声明和通用装配机制：声明应用名称、构建产物及其页面与资源挂载规则，框架负责校验和分发。新增应用只需提供声明与产物，不应修改宿主代码、复制应用专属中间件或为应用名新增分支。路由冲突、API 边界、资源缺失及路径穿越必须明确处理；若声明规则不足以表达实际需求，先扩展通用契约而非增加特例。

实现和验收须核对开发、单文件及分离部署的入口、资源、深层路由、缺失资源和应用隔离，并通过增加第三个应用验证扩展能力。改变一个应用的挂载路径或资源不应改变其他应用；共享能力通过公开接口接入。

## 依赖原生模式优先

实现功能前，先识别项目已使用的相关依赖，查当前版本是否已有对应场景的官方推荐模式、完整示例和现成机制，再确定实现方式。查的不只是“有没有组件或函数”，还包括官方如何组合能力、保存状态、连接事件、处理异步结果与管理生命周期。适用于前后端框架、表单、数据请求、状态管理、动画、资源装配等，不限于前端组件选型。

优先依次复用项目已有的有效接入、依赖官方推荐模式及原生能力；已有依据须核对版本与当前场景，已有代码偏离官方约定时重新判断。按项目文档检索约定查证，必要时核对安装版本源码，围绕本次场景查完整数据流，不只摘一个API签名。记录采用的模式、适用理由和实际接入位置；短任务在当前任务说明中简述即可。

先用依赖规定的状态来源、组合方式和生命周期完成接入，再补业务逻辑。官方方案不适配时，明确具体约束、已核对的能力及缺口，比较已有依赖或成熟替代，再选择最小适配。不能仅因会写、实现短或已有测试通过就自行维护一套等价机制，也不能只用了库的组件外壳就认定遵循了原生模式。

设计、编码与审查核对实际接入是否遵循所选模式；自定义状态、effects、事件、定时器与资源管理代码须能说明原生模式为何不适用。验收同时验证接入方式及实际行为：功能成功不能替代模式核对。若依赖已有适配方案而实现遗漏，回到原生模式修复，不继续堆补丁。

## 行为过程与生命周期

在核对[依赖原生模式](#依赖原生模式优先)的基础上，沿一次实际操作推演完整过程，再安排状态与代码：从谁触发、哪些状态改变、过程中用户或调用方观察到什么，走到完成后的收尾。每个异步或延后阶段都判断当前仍需哪些数据、哪些不变量必须成立；过程中的可见状态与最终结果同属正确性。局部改动可直接在当前任务说明中讲清，不额外要求状态机框架或完整设计文档。

以使用者和消费者的需要决定状态归属与生命周期。操作发起、结果生效、呈现完成、数据或资源可释放，可能发生在不同时刻；只有实际已无人使用时才清理。生命周期不同的状态按职责分开，需要一起成立的数据保持一致，避免为了少一个变量把互不等价的状态绑定。先查框架的状态、完成/退出回调、取消与资源管理机制，以实际事件驱动衔接，不靠猜测时长或偶然执行顺序维持正确性。

实现时沿改变状态的入口走查所有消费者及后续回调，核对中间状态、完成条件与清理顺序，并按本次风险处理失败、中断、重复操作或旧任务晚到。检查重点是用户或调用方是否始终得到连贯、有效的行为，而非每个局部函数各自执行成功。

验证围绕这条行为链选择实际时序与边界，观察关键过渡及收尾后的再次使用。最终结果断言、静态截图或测试通过数量不能替代过程中不变量的验证；发现遗漏时修正状态与生命周期设计，而非仅在出现症状的位置加延迟、兜底或新特例。仅执行本次适用的场景，不机械展开所有异常组合。

## 扩展槽位与链式透传

模块通过 Fx 的 `group:"..."` 值组和 `Provide*` 注册参与装配；这些槽位是共享扩展点，按**最弱机制优先**选择参与方式，越强的机制越要保留其他模块的贡献：

| 机制 | 能力 | 约束 |
| --- | --- | --- |
| 只读监听（事件、`group` 消费） | 只观察 | 不改写、不截断 |
| `Provide*` 值组注册 | 追加一项贡献 | 不改变其他项；名称或标识重复时按装配约定拒绝，不静默覆盖 |
| 链式 `Operation(ctx, next)`（waterfall） | 可改写上下文、可拦截 | 不拥有决策的中间件**必须调用 `next(updated)` 透传**；改写决策时保留已有字段，不整体丢弃 |
| 唯一槽位构造器 | 独占一个能力 | 多实现显式失败，不按加载顺序挑选 |

`HTTPMiddleware.Operation` 是 waterfall 链：多个模块按 `Order`（同序按 `Name`）依次执行，前一环通过 `next(updated)` 把上下文交给下一环。**只有明确拥有该决策的模块才可不调用 `next`**；否则会静默截断请求链，使后续中间件与业务处理器都收不到请求。改写时传播上游已设置的上下文值，不重建全新 `huma.Context`。

槽位按容量分为两类，模块作者须在提供 `Provide*` 契约时明确属于哪一类：

- **可叠加**：值组聚合多个贡献（如 `redberry-http-middleware`、`redberry-commands`、`config-checks`），按稳定顺序消费。
- **唯一**：恰好一个实现（如 `auth-accounts`），多于一个时装配期显式报错，不回退、不覆盖。

`redberry inspect` 是只读的静态装配视图，用于查当前安装图里有哪些槽位、每个槽位在哪些模块与源码行被引用；它列出**事实**（标签出现处），不推断槽位语义。语义以本节与提供该槽位的模块公开契约为准。新增或改动槽位时，同步更新提供者的 `Provide*` 文档与本节分类，并用 `redberry inspect --group <槽位名>` 核对注册点。

## 错误反馈与诊断

涉及用户操作、失败处理、后端执行或性能分析时，读取[错误反馈与诊断](diagnostics.md)。前端反馈帮助用户纠正操作；后端日志帮助开发者排查程序故障和定位性能瓶颈。正常操作错误向用户反馈，程序／依赖故障和耗时点进入诊断日志，按对应判据分别验收。

## 规则执行方式

命名与代码风格优先遵循 Go、TypeScript 及已选框架的社区惯例；需要统一跨模块行为时补充项目规则。规则正文在对应专题维护，Skill 引用规范。

| 规则范围 | 执行方式 |
| --- | --- |
| 格式、导入顺序、基础语法与类型 | 格式化工具、Lint、编译与独立类型检查 |
| 模块依赖方向、公开入口、生成代码边界与 UI 使用范围 | 静态检查，统一接入 `redberry check` |
| 文件名、标识符及 API 字段命名 | 遵循既有规范，可自动检查的部分接入工具 |
| 职责划分、抽象与设计模式 | 编码 Skill 指导设计与自查，结合代码审查 |
| 调研、POC 与测试覆盖 | 编码 Skill 要求提供来源、验收条件及实际验证结果 |

阶段选择与交接以 `using-redberry` 及对应专业 Skill 为准；资源维护边界见[设计与架构](design.md#编码-skill)。

## 文件与公开入口

- Go 模块文件在各自模块根；项目启动入口是 `cmd/<项目命令名>/main.go`，装配位于同目录 `bootstrap.go`。
- 模块后端入口为 `backend/redberry_module.go`，导出 Fx `Module`；前端公开入口为 `frontend/index.ts`，使用具名导出。
- 跨模块只通过公开入口引用，包括类型；模块内部可引用自身实现。私有目录的 `index.ts` 不自动成为公开入口。
- 自有模块放项目内的模块目录，ID 后缀即该目录；外部依赖及生成产物在 `.redberry/`，整体 Git 忽略且可恢复，不保存业务自定义。
- `migrations/` 放模块根，与 `backend/`、`frontend/` 平级，不把各模块 SQL 复制到项目根。

具体文件见[目录结构](structure.md)，依赖、替代与生命周期见[模块与依赖](modules.md)。

## 依赖与生成

- `redberry.yaml` 管模块依赖，`redberry.lock` 锁定实际选择；Go 和前端包仍通过各自依赖文件管理。
- `deps` 支持精确版本和 `^`；`replaces` 只声明目标大版本，同一目标全项目使用一个实现。
- CLI 维护源码、工作区与生成装配，用户不手工维护 Go 本地映射；生成文件不手改。
- 依赖维护操作不能删除自有模块源码；检查不通过覆盖生成文件掩盖不一致。

完整规则见[模块与依赖](modules.md)、[CLI 约定](cli.md)。

## 后端业务

- 业务依赖通过构造参数传入，容器操作集中在装配层；资源获取与释放交给 Fx 生命周期。
- 运行配置只通过统一入口加载，显式零值参与覆盖，合并与校验通过后才注入；修改后重启生效。
- Go 类型与注册生成 OpenAPI；业务返回普通 Go 错误，由接口层映射 Huma 原生错误响应。
- 列表使用 `page`、`size`，响应返回实际分页值；常规编辑使用完整 `PUT`，区分未传、null 与零值。
- 大整数资源 ID 使用字符串；普通业务时间点统一 UTC、毫秒精度，纯日期保持字符串。
- 项目迁移按[数据迁移](migrations.md#迁移事务与失败处理)约定执行，事务能力遵循数据库方言；普通业务事务由业务边界管理。

新增或调整用户可见的后端错误、校验消息与其他响应文字时，读取[国际化契约](i18n.md)及[错误响应国际化](api.md#错误响应国际化)。细则见[配置](config.md)、[API 契约](api.md)、[数据迁移](migrations.md)。

## 前端业务

- 业务 UI 使用 TSX，通过有限 UI 入口组合页面，沿用统一主题；内部样式由基础 UI 按需使用 CSS Modules。
- 模块引用按真实文件归属检查，覆盖别名、软链接及再导出；动态导入使用固定字面量。
- 通过生成的 Fetch / Query 入口访问 `/api`；强校验约束代码和边界，不增加重复的客户端请求、响应 Schema 校验。
- Router URL 保存列表条件；分页以对应服务端响应为准，Table 的字段与页码转换集中在边界。
- TanStack Form 管编辑状态，Zod 管表单业务校验；保存位于 `onSubmit`，字段错误用原生提交错误槽回填。
- 日期与时间控件沿用 Mantine dates；纯日期不做时区转换，时间点显示和编辑默认按[用户本地时区](frontend.md#本地时区)处理，并保留未修改的原始值；接口收到的有效偏移不能直接作为显示时区。

新增或调整界面文案、模块页面及语言格式时，读取[国际化契约](i18n.md)与[前端国际化](frontend.md#国际化i18n)，贯通语言范围、资源装配与实际验收。主题、控件、状态与错误处理见[前端开发](frontend.md)。

## 运行、检查与发布

- 项目统一入口为根 `package.json` 的 `dev / gen / check / test / build / build:split` 脚本；命令采用子命令在前、参数在后的写法。
- `pnpm dev` 默认 dev 环境；后端手动重启，前端使用 Vite HMR。构建不携带运行配置，发布模式由 `pnpm build` 与 `pnpm build:split` 选择。
- 统一检查覆盖业务、模块和生成代码，业务不自行关闭既定规则；Vite 构建与测试不代替独立 tsc。
- 测试默认零重试，统一入口校验必需层、退出码与结构化报告；空集合和异常报告不能视为成功。
- CI 先恢复依赖和必要产物，再执行 `check` → `test` → `build`。检查不自动修复。

命令与进程行为见[CLI 与开发流程](cli.md)，工具版本和测试层次见[技术选型](stack.md)。
