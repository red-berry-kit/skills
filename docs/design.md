# 设计与架构

## 项目定位

红梅（Red Plum）是一套面向 Agent 辅助编程的 Go 业务项目模板。它提供可组合的基础能力、统一约定和静态检查边界，让开发集中于业务功能。

项目包含后端、前端、skill / tool 三部分，独立处理、按需加入。当前 Agent 开发的重点是编程过程中的约束，让开发者和 Agent 从类型、约定与检查结果中获得明确反馈。Agent 文档入口、工具职责和任务流程见下述设计；交付状态见[实现范围](status.md)。

项目共用一套结构，业务模块按需添加。具体业务模块分别设计，不预先固定全部功能。

## 设计原则

| 原则 | 约定 |
| --- | --- |
| 约定优于配置 | 约定路径、入口和资源位置，避免模块重复声明 |
| 清晰且简短 | 兼顾语义和链路一致性，在此前提下简化命名 |
| 模块独立、按需组合 | 用户业务也是独立模块，前端、后端及资源按需提供 |
| 基础集中维护 | 基础模块与公共工具统一维护，使用方按版本升级 |
| 静态边界明确 | 类型和现成规则能检查的约束交给工具 |
| 减少定制 | 优先依赖原生能力与标准格式，缺口才补小范围适配 |
| 先验证再决定 | 关键选型通过实际接入验证，保留能力限制 |

## 模块如何组合

每个模块拥有独立的身份、版本、依赖和公开入口。后端通过 Fx 组合构造器与生命周期；前端通过静态可见的入口和完整路由树保留类型关联。

CLI 管理源码、版本、工作区和装配输入，依赖注入负责对象和资源的组合。两者共用模块图，不让业务分别维护脱节的安装与装配步骤。

自有模块放项目内的模块目录，外部源码放 Git 忽略的 `.redplum/modules/`。项目提交 YAML 清单和锁文件，以便团队与 CI 恢复依赖。自定义行为留在业务模块或独立实现中，外部目录不作为长期修改基础源码的地方。

替代实现通过 `replaces` 声明目标模块 ID 与大版本，消费方继续依赖目标约定。同一目标只允许一个实现，选择后全项目生效；替代维护者负责遵守约定，框架执行正常编译与边界检查，不另建健全性评估机制。详见[模块与依赖](modules.md)。

## 业务开发链路

```text
模块源码与依赖清单
    → CLI 安装、解析与装配
    → Fx 后端 / 前端入口与路由
    → 业务接口与 TSX 页面
    → 统一检查、测试与构建
```

API 以 Go 类型及接口注册为来源，经 Huma 生成 OpenAPI，再由 Orval 生成类型、Fetch 调用与 Query 接入。前端各部署形式统一使用 `/api` 相对路径，不手改生成代码。

成功响应使用业务结构，失败沿用 Huma ErrorModel。列表使用 `page`、`size`，以服务端返回的实际分页值为准；常规编辑采用完整 PUT，区分必填、可空与零值。ID、时间日期和错误状态遵循统一[API 契约](api.md)。

前端使用 React / TSX 与 Mantine 的有限公共入口。主题、布局语义和静态边界约束风格；Router、Query、Form、Table 分别承担自己的状态职责，日期与错误处理沿用现有组件能力，见[前端开发](frontend.md)。

强校验针对代码、类型、规范和模块边界，不要求客户端重复执行请求、响应 Schema 校验。服务端输入校验与表单业务校验保留各自职责。

## 配置与迁移

模块用 Go 类型声明配置，项目统一生成编辑 Schema、合并公共与环境配置、校验后注入。配置在启动时固定，构建不携带部署配置；HTTP 与配置共用 Huma 校验体系，见[配置](config.md)。

迁移资源属于模块，执行批次属于项目：所有本次待执行迁移及版本记录在一个事务中统一提交或回滚。并发启动先取得数据库迁移锁，再读取版本与执行；该事务范围不扩展到普通业务操作，见[数据迁移](migrations.md)。

## 工程入口与交付

### Agent 文档入口

项目根 `AGENTS.md` 是 Agent 开发的统一入口，由 `redplum create app` 初次生成，简要说明项目结构、常用 CLI 与项目任务命令、用户模块和 `.redplum/` 生成目录的边界，并留出项目特有规则区。可提示使用用户已安装的 Red Plum Skill，不绑定客户端路径；不复制完整规范。创建后由业务项目维护，后续 CLI 操作、Skill 或官方规范更新均不覆盖。

具体任务按需提供 Skill，以 `SKILL.md` 描述任务流程，并按需配套脚本和参考资料。官方 Skill 发布包携带该 Skill 实际需要的规范资料，放在 Skill 目录的 `references/` 下并使用包内相对路径；参考资料由独立 Skills 仓库的 `docs/` 生成，同 Skill 使用相同版本。用户自行获取、安装和更新 Skill 包，安装位置遵循所用客户端的约定。

公开文档站提供 `llms.txt`，作为面向 AI 的文档索引，从文档结构生成并链接详细内容。它承担网站资料导航；项目开发规则由 `AGENTS.md` 承载，任务流程由 Skill 承载。具体自动发现与加载行为取决于所用 Agent 客户端。

### 开发工具入口

Red Plum CLI 负责从项目模板和模块模板创建项目与模块，并维护项目声明的模块依赖；CLI 将输入填入模板，再执行必要的依赖接入。项目任务脚本提供统一的生成、检查、测试、开发和构建入口，具体命令以目标项目定义为准；任务调用 Red Plum CLI、编译器、静态检查器及测试工具完成工作。

Skill 说明何时使用 CLI 或项目任务入口、如何判断结果并继续工作，不重复实现命令能力。业务运行时供 Agent 调用的工具按业务模块需要单独设计，不预设通用工具集合或统一注册层。

### 编码 Skill

Red Plum Skills 的统一入口为 `using-redplum`。入口负责阶段选择、任务恢复和交付；每个专业 Skill 的执行步骤、出口和交接以其 `SKILL.md` 为唯一流程定义。本页只说明资源边界，不再复制流程表。

项目 `AGENTS.md` 应指向已安装的 `using-redplum`，由入口按任务选择专业能力。具体发现、读取或调用机制遵循所用客户端；源码目录不等于客户端安装目录。缺少某项 Skill 时应说明缺失并继续有依据的工作，不伪称已使用。

### Skill 组织与维护

- Skill 源码在独立 Skills 仓库根的 `<skill-name>/SKILL.md`；名称与目录一致，统一入口为 `using-redplum`，专业 Skill 使用 `redplum-` 前缀。
- `description` 用英文描述触发条件，正文与说明用中文。入口组织流程，专业 Skill 定义阶段要求，技术规范按需引用。
- 需求、计划与验收分别由 `redplum-requirements`、`redplum-planning`、`redplum-verification` 承担；调研、设计、POC、编码、排障和审查保持各自职责。新增 Skill 应有独立触发场景，补充说明可保留为参考文件。
- 规范在本 Skills 仓库的 `docs/` 单点维护；`scripts/sync-references.py` 将规范同步至已有的 `references/`，保证单个 Skill 内的相对链接可用。无需技术规范的 Skill 保持自包含。
- 任务流程直接修改对应 `SKILL.md`，不在规范副本重写；新增或修订流程先建立行为对照，再验证阶段选择、产出与交接，检查实际行为，不能只匹配标题。
- 项目 `AGENTS.md` 只保留使用入口及项目特有规则，由项目维护。用户独立安装和更新 Skills，Red Plum CLI 不管理、不覆盖它们，`.redplum/` 不保存 Skills。
- 源码更新不等于所有客户端已加载；安装后核对实际路径，发现目录可能需要客户端重新扫描。未安装的下游 Skill 不能作为已执行的证据。

### 任务与发布

项目通过已有任务入口统一生成、检查、测试、开发和构建；应用使用独立子命令检查配置、迁移和启动服务。构建支持前端嵌入的单二进制与前后端分离形式，详见[CLI 与开发流程](cli.md)和[目录结构](structure.md)。

技术及固定版本见[技术选型](stack.md)，日常规则索引见[开发约定](conventions.md)。正式模板、CLI 与公共组件的交付状态独立列在[实现范围](status.md)，不以局部 POC 代替正式实现。
