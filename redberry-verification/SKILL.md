# 红莓实现验收

按验收条件、实施范围、当前源码与环境、原始检查证据验证可观察行为。已有实现也按本 Skill 验收。

## 选择验收方式

每次按当前改动的影响范围、风险和用户要求选择。默认当前 agent 验证；能力复用、文件数量或上一轮使用了子 agent，本身不构成独立验收理由：

- **小改动由当前 agent 直接验证，不派子 agent**：边界清楚、影响有限且不触及下述高风险条件的调整。
  - 执行受影响的现有检查，从实际入口操作受影响行为：界面用真实浏览器检查显示和交互；请求接入真实后端，观察结果及失败反馈。
  - 组件测试、Mock 和截图仅作补充，不能单独替代真实使用验收。复用未受影响证据，不默认重跑全套测试、完整截图矩阵或重新创建消费应用。
  - 在对话中简述结果即可，无需新建验收报告。
- **高风险或明确要求时独立验收**：认证／授权边界、破坏性协议或数据迁移、跨模块默认装配；复杂共享状态在多个入口传播且现有检查不足以覆盖时同样适用。独立验收前简述具体风险，按下节交接。

小改动发现超出局部范围的问题时，重新评估受影响链路并升级验证；检查通过后及时收尾。用户明确指定的验收方式优先，无需为常规选择另行请求确认。

## 干净验收者与交接

首次独立验收使用未参与实现的子 agent，并通过当前工具提供的隔离机制关闭会话继承。修复后复用该验收者，提供变更与失败项，只复验受影响范围；验收者参与了实现、上下文已不可用或用户要求重新独立审查时才换新。验收者不递归派发。

交接材料包含：

- 用户确认的范围与完整判据、项目规则和必要 Skill 路径。
- 当前源码位置及版本／快照、运行环境和实际任务入口、允许的测试操作与资源边界。
- 原始日志、触发条件与复现证据；不附实现者自评、推测根因、推荐修法或预设通过结论。
- 涉及参考界面时，提供实际参考页面／源码及已确认差异，不以口头描述代替。

验收者先独立核对完整范围，再核实历史问题；按需查阅实现过程记录。

验收者实际读取本 Skill 和必要规则，独立选择并执行检查，报告事实和缺项。可在隔离范围补充测试、复现脚本和证据；不修业务实现、调整需求或替实现者选定修法。验收期间固定被测源码，主 agent 不并发修改；内容变化时作废受影响结果并重新交接。无法创建独立上下文时如实报告能力缺口，已有自检仅作为自检证据。

涉及多个应用的资源、路由或交付时，按[独立应用边界](https://raw.githubusercontent.com/red-berry-kit/skills/main/standards/design.md#独立应用边界)核对声明驱动装配、应用命名、路径冲突与跨应用隔离。

## 执行

1. 先建立判据与记录结构，再判断结果：
   - 分开建立“适配核对”与“行为实测”两类判据，各有结果和依据；任一必需项缺失或未通过都不用另一类的通过结果替代，必需项判为不适用时须写明理由。
   - 涉及模块能力时，读取实际安装版本的 `README.LLMS.md`，将全部适用使用契约、设计及行为验收要求纳入判据；用户指定参考时同时纳入已确认的对照要求。
   - 建立对应表：**验收条件／实际入口与场景／验证方式／结果／证据**；结果区分通过、失败、未执行及有理由的不适用。
   - 界面、用户可见 API 消息或语言格式的交接材料须含项目 i18n 约定及语言范围，据此安排受影响前后端消息、格式和装配的实际验收；缺少约定时返回需求阶段明确。
   - 先核对范围完整性再判断结果；缺少判据时返回需求阶段，不按现有测试反向缩小需求。
2. 核对证据有效性：
   - 按[依赖现有能力优先](https://raw.githubusercontent.com/red-berry-kit/skills/main/standards/conventions.md#依赖现有能力优先)分别核对接入模式与行为证据。
   - 核对原始证据对应的源码、配置、依赖、环境和用例；由验收者决定复用哪些未受影响的检查，并写明理由。
   - 实现、配置或环境发生相关变化时，本轮实测受影响的关键场景；修复后必须重验原失败、受影响部分和必要回归。
   - 仅补选型依据且实现与环境未变时，核对补充依据，复用仍有效的行为证据即可。
   - 以原始证据核验，不以实现者的通过摘要代替。构建、类型检查、局部测试、POC 和生产环境验证分别说明范围，不能相互替代。
3. 从项目实际任务入口执行必需检查及风险相关测试：
   - 新增或改变可复用模块的默认装配与核心能力时，必须在干净应用通过真实 CLI 添加，只填必要配置即可运行核心能力。人工改动须记录；模块专属接线不算必要配置。示例应用不替代安装验收，本地来源或隔离版本夹具注明覆盖范围。
   - 按第1项判据核对能力适配，按第2项确定需实测的范围；界面必须使用真实浏览器操作，请求必须接入真实后端，观察结果及失败反馈。按受影响模块的契约验证设计、行为与边界；有参考界面时逐屏对照实际参考与已确认差异。必需项缺失不判通过。
   - 按[行为过程与生命周期](https://raw.githubusercontent.com/red-berry-kit/skills/main/standards/conventions.md#行为过程与生命周期)验证用户操作到最终状态的真实调用链，观察适用的关键过渡与再次使用；共享机制须覆盖所有受影响入口。
   - 按变化选择失败、恢复、并发或持久化场景，不为每类任务跑全套测试。
   - 操作、请求或后端执行按[错误反馈与诊断](https://raw.githubusercontent.com/red-berry-kit/skills/main/standards/diagnostics.md#验收)分别验证正常操作错误、程序／依赖故障与性能耗时，记录实际界面与日志结果。
4. 对失败、覆盖缺口或可疑结果记录编号、对应判据、预期与实际、复现条件和原始证据，交回主 agent 按 `using-redberry` 的修复闭环处理。验收者不边修边宣告通过；测试修订必须保持业务判据，不能删除失败用例或降低约定来获得绿色结果。
5. 环境不足时先检查已有配置能否提供不干扰用户服务的独立验证方式。可用替代环境只证明其范围；记录仍缺的条件、受影响验收项与恢复步骤。只清理本次创建的资源。

完成条件：每个验收项都有「验收条件／入口与场景／方式／结果／证据」，通过项的证据来自本轮执行或写明复用理由。

## 出口与交接

按验收方式输出结果：小改动简述实际检查、结果及缺项；独立验收输出**轮次与验收者标识、源码基准、环境、逐项验收表、实际命令及结果、证据位置、复用依据、问题与未验项**，交回主 agent 更新同一任务记录。必需项全部通过才标记本轮验收完成，普通任务由当前 agent 复查差异，复杂变更按需交 `redberry-code-review`；本轮检查已通过且无新增变化时不重复运行。

必需项失败或未执行时标记部分完成，继续可执行工作。若用户只要求验收，则以验收报告收尾，不自动修复或发布。
