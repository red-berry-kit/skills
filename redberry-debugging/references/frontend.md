# 前端开发

前端采用 React、Vite、TypeScript / TSX 与 pnpm。技术及版本见[技术选型](stack.md)，目录与依赖归属见[主入口与工作区](structure.md#主入口与工作区)。

## UI 与样式

采用 Mantine + CSS Modules，不引入 Tailwind CSS。

所有前端新增、改造及审查均优先遵循所用版本的 Mantine 官方文档与设计语言。实施前核对涉及组件的官方用法、变体、状态和交互；优先使用原生组件、公开 props 与主题能力，不凭印象重做已有能力。外部案例用于参考页面布局、信息层级与业务交互，控件外观、状态及动效先按 Mantine 实现，不以复刻案例为由覆盖组件内部皮肤。

主题色、默认圆角、字体、间距及密度由基础 UI 的统一主题配置管理。组件默认继承主题，自有布局使用主题变量；禁止页面或普通控件写死主题色、圆角形成另一套风格。危险操作、错误等语义色和头像等固有形状可按组件语义保留，不能借例外覆盖普通操作。原生能力不足时，先记录具体缺口，再在有限 UI 内补充最小实现，保持主题、无障碍、国际化和减少动态效果契约。

验收除检查当前外观，还须针对修改涉及的主题属性切换配置，确认表格、面板、输入与操作等受影响入口共同生效。绕开适用原生能力、无依据覆盖皮肤或普通组件不随统一主题变化，均列为必修问题。

使用 Mantine 作为统一基础 UI。基础 UI 模块集中维护主题、颜色、字体、间距、密度和常见页面结构，业务通过有限组件入口组合界面。

业务入口暴露操作意图、密度等语义参数，避免直接透传完整底层样式能力。基础 UI 内部按需使用 CSS Modules；CSS Modules 负责隔离内部样式，不负责自动保证设计一致。

Mantine 默认主题可以被覆盖，因此“使用同一 UI 库”不等于“已强制全部页面风格一致”，仍需入口规则和实际页面检查。

业务 UI 使用 TSX 标签语法。`@mantine/hooks` 的行为 hooks 可按依赖规则直接复用；这不开放 `@mantine/core`、日期组件或 CSS 的业务直接导入。业务目录限制底层 UI/CSS 直接导入、createElement/cloneElement 等元素创建入口；正常命名 hooks 与合法属性展开保留。样式展开补充检查只处理静态可见类型，不是一套新的 CSS 语言或运行时安全机制。

## 能力复用与 Hooks

实现、改造或审查前端功能时，先按场景检索所用版本 Mantine 的组件、`@mantine/hooks` 目录与官方文档，并核对项目已有封装和依赖提供的能力；官方能力不适配时再检索成熟社区方案，最后才考虑自行实现。该规则覆盖行为逻辑，不只覆盖可见组件：存储与跨标签同步、全屏、媒体查询、尺寸观察、事件订阅、点击外部、焦点管理、防抖节流、剪贴板及过渡等均需核对。检索方向不等于指定某个 Hook 必然适配。

已有能力满足场景时必须复用，不能因实现短小、已写好或自测通过而重复造轮子；项目已定的状态、数据请求等职责继续由既有方案承担，不能因发现新 Hook 无依据迁移。比较社区方案的需求匹配、维护与版本兼容、类型、许可、依赖成本、清理与卸载、SSR／浏览器支持及相关无障碍能力，按项目依赖规则引入，不为单个简单动作堆叠依赖。

实施前留下简要选型依据：候选及对应版本的官方文档／源码、可复用能力、实际缺口和最终采用方式；短任务记录在当前任务说明即可。自行实现必须说明 Mantine、已有依赖与合适社区方案为何不适配，仅实现缺失部分。引用已有有效调研时核对版本与范围，不机械重复检索。

审查沿自有 effects、事件监听、定时器、存储及浏览器 API 包装追踪对应选型依据；存在适用现成能力而无合理理由自行实现，或未检索就声称没有，属于必修问题。验收验证真实行为、边界和卸载清理，不能只检查 Hook 名称；静态检查通过不证明复用选型合格。

## 组件选型

新增、改造或审查前端功能时，逐项按用户场景选型，不能把“同属 Mantine”“已有代码能用”或“测试通过”当作适配结论。组件和行为 hooks 均执行以下闭环：

1. **明确约束**：先核对[设置作用域与字段语义](#设置作用域与字段语义)，列出涉及的输入／操作语义、取值范围、选项数量与是否需要并列比较、关键状态和交互，以及键盘、国际化、主题和窄屏要求。业务规则与控件能力分开，不按现有实现反推需求。
2. **检索比较**：按[能力复用与 Hooks](#能力复用与-hooks)查当前版本的官方目录、文档与已有能力，纳入能直接表达场景的专用组件／hook，与当前或通用方案比较。只比较真实适用候选；没有合理备选时写明依据，不强凑数量，也不无限穷举社区方案。
3. **形成决定后实施**：在已有任务记录中保留“场景约束 → 候选及版本来源 → 采用／排除理由 → 实际验证点”。短任务一条简要记录即可，不要求单独文档、额外审批或无关阶段。专用能力已适配时必须复用；需自制时说明原生及现有方案的具体缺口，只补缺失部分。名称、宣传及主观偏好不是排除依据。
4. **按决定核对实现**：追踪共享入口及项目／模板副本，确认实际使用所选组件的原生能力，没有用包装名掩盖通用拼装。实现中约束变化时更新选型决定，不先做完再以“已实现”补理由。
5. **分别验收适配与行为**：适配结论核对候选覆盖、来源、约束和取舍；行为结论通过实际入口验证选中状态、关键交互及适用的键盘、翻译、主题、窄屏等。分别写明通过、失败或缺项，任一必需部分失败／未验证均不能判整体通过。功能测试通过不能替代适配核对，选型记录齐全也不能替代实际操作。

审查者从需求约束重新核对选型依据，不因实现者已选定某组件就接受该结论。**漏查适用专用能力、使用通用方案却无充分依据、只证明能用而未核对适配，均列为必修问题。** 缺依据时先补查，不能将证据不足直接写成“不支持”，也不能仅凭个人审美要求替换组件。

先判断用户是在即时调整设置，还是填写待提交的数据／查询条件，再比较控件。选项数量只是约束之一，还要考虑并列比较需要、填写习惯、整张表单的一致性与空间密度；不能仅因选项少就使用分段选择，也不能把所有字段统一为 Select。密码、日期范围、分页、导航、颜色等只是回归样例；上述步骤适用于未列举的组件和行为，不能用持续堆积样例替代流程。

## 表单整体设计

新增表单、调整布局或在已有页面增加字段／操作时，先完成页面任务设计，再做[组件选型](#组件选型)。复用结论限定到已有证据覆盖的层级：控件可复用，页面的任务分组与交互仍需核对；已有页面方案覆盖本次任务、状态和宽度时可直接复用。

1. **任务设计**：按用户要完成的任务确定只读资料、可编辑字段、操作频率、提交边界及默认／按需展示内容，再一起安排字段和操作区。推演默认、展开、提交、失败、取消及再次打开等适用状态，明确输入保留、焦点与敏感数据清理。**完成条件**：能说明每组内容为何同处一处、何时显示、怎样提交和结束；已有任务记录或对话中留一条简要决定即可。
2. **布局与选型**：根据上述决定核对依赖的完整推荐模式，按实际容器宽度、输入内容和译文长度安排顺序、列宽、密度、对齐与操作位置。列数和操作是否独占一行由任务决定；原生能力有明确缺口时作最小适配。**完成条件**：默认态和按需展开态均完整可用，受影响宽度下字段与操作可达，所选组件及组合有依据；此时开始实现。
3. **设计验收**：从实际入口检查任务组织、默认展示、密度、留白、对齐与操作可达；覆盖受影响断点附近及适用的状态过渡，结合实际操作、截图和必要边界证据。**完成条件**：分别给出整体设计适配与业务行为的结果及依据；提交成功、控件不溢出分别只证明对应行为和边界。存在设计缺项时补齐后再判整体完成，复用未受影响的有效证据。

标题按[命名判据](conventions.md#命名判据)利用上下文保持简洁。任务决定布局与验证范围，具体页面的分区、列数或弹窗方案只作为该任务的决定。

## 设置作用域与字段语义

主题、语言等应用级设置由应用壳层或统一设置入口控制，业务页面、表单、模态框和抽屉继承其状态。按入口的实际使用场景判断职责；仅独立入口确需提供设置时在该入口配置，业务容器不因被复用或需要测试切换而重复放置全局操作。只有明确需求定义了独立的局部设置，才展示对应局部入口及其作用范围。验收从统一入口设置后检查业务容器继承结果；编辑中的全局状态更新通过组件或集成测试验证输入、错误与焦点保留，不为满足旧测试保留多余产品入口。

表单字段区分**字段名称**与**当前值／状态**：每个字段具有稳定、可见、与控件关联的标题，Switch 等布尔控件也遵守同一要求；“启用／停用”“是／否”等状态文案只能补充状态，不能替代字段标题。通过 Mantine 的 label、Input.Wrapper 等公开能力关联标题、说明与错误；原生控件已有完整字段标签且能明确表达该字段时不重复增加标题。Tooltip、placeholder 和不可见的 aria-label 不单独充当可见字段标题。

实施与审查枚举受影响设置的归属和全部字段，分别核对入口是否属于该容器、字段标题能否独立说明编辑对象。验收覆盖中英文、开关两态和窄屏：标题保持稳定且可见，可访问名称指向字段，当前状态可辨；模态框等业务容器继承全局设置且只包含本任务操作。重复全局设置入口、字段只剩状态文字或靠位置猜含义，均为必修问题。

## 按钮图标

新增、修改或审查用户操作按钮时，**每个按钮必须采用“语义图标＋文字”或纯图标形式**。覆盖工具栏、搜索／重置、表单提交、表格行操作与排序、空态／错误恢复、返回、登录／退出及刷新等操作；通过有限 UI 入口传递明确的操作图标，不按翻译后的文字猜测图标，不以“原有按钮可用”豁免。适用按钮缺少可见图标属于必修问题。

表格行内的编辑、删除等操作统一使用纯图标按钮，并提供国际化可访问名称及悬停、键盘聚焦提示。

图标须表达实际操作并保持同一视觉体系；文字按钮中的装饰图标对辅助技术隐藏。空间紧凑时使用组件库专用的纯图标按钮，提供国际化的可访问名称；所有面向用户的纯图标操作按钮均须提供国际化 Tooltip，并同时支持鼠标悬停与键盘聚焦；不能以“图标常见”豁免。纯图标不能以无名称、仅有颜色或仅有鼠标悬停提示作为完成依据。日期、页码、选项等组件内部的数据选择项保持原生语义和形态，按所属专用组件验收。

触发菜单、弹出框或抽屉的按钮，在浮层关闭时提供悬停／聚焦提示；浮层打开后隐藏或禁用对应 Tooltip，避免遮挡内容，关闭后恢复提示能力。该状态互斥符合提示规范，不能通过抬高层级或让 Tooltip 持续覆盖操作区满足“必须有提示”。验证至少覆盖关闭态触发、打开后消失、关闭后再次触发及浮层操作可达。

审查与验收先枚举受影响页面及共享入口中的纯图标操作按钮，记录名称、所在页面／状态、Tooltip 悬停结果与聚焦结果，覆盖顶栏导航、主题、语言、全屏、设置和行操作；共享控件还需追踪登录页、工作台与抽屉等调用入口。`aria-label`、原生 `title`、悬停打开菜单、源码存在 Tooltip 均不能替代实际提示验证。缺少任一触发方式或译文属于必修问题；未逐项验证的入口明确记为缺项，不凭相邻按钮通过推定全部通过。组件内部的关闭、清除等控件先按所属专用组件的原生交互规范验收，避免破坏库行为。

实现后从实际页面逐项检查可见图标、图文对齐、按钮主次、加载／禁用、键盘和名称翻译；窄屏检查图标加入后是否造成按钮换行、文字或邻接输入裁切。检查项目及模板的对应操作，不能只修改示例或只增加规则文案。

## 界面参考与用户文案

用户指定参考项目或案例时，先核对其实际页面或对应版本源码，记录本次涉及页面的结构、标题与副标题的有无及层级、字号字重、对齐留白、操作位置、触发方式（点击／悬停／键盘／触屏）、切换顺序与当前选中状态，以及亮暗色和语言状态。将参考事实与本项目取舍分开；有意偏离须有需求或已确认约束支撑。不能只借配色、套一张卡片，就认定已实现参考风格。

按钮、菜单、标题和提示按[命名判据](conventions.md#命名判据)从用户场景与操作目的命名，利用页面上下文消除重复词；中文、英文分别使用当地自然的简洁表达，不逐字照搬冗长文案。实施、审查与验收均在实际页面及共享入口中核对，已确认的简洁命名要求不能降为个人偏好；不能为缩短可见文案牺牲可访问名称或必要的风险说明。

可见内容以使用者完成任务所需的信息和操作为边界。协议、加密方式、代理配置、调试状态和开发／部署解释进入对应文档，不因为实现了某项技术就自动增加提示框、副标题、说明文字或页面。只有需求明确、且确实帮助使用者操作或判断的内容才进入界面；必要错误提示给出可执行反馈。

演示和验证界面不直接成为正式用户流程。会话恢复、Token 刷新等基础机制按产品约定自动完成，界面只呈现必要的加载、失败和恢复操作；不自行新增手工恢复按钮、Token 控制台或登录后的认证成功状态页。实际业务账户页等明确需求按各自职责实现。

用户要求组件库原生质感时，通过组件组合、公开排版与语义参数实现参考层级，不覆盖组件内部样式复刻另一套控件皮肤。具体参考项目、视觉数值与组件约束由目标项目规范确定，不把单个案例固化为所有项目默认主题。

验收逐屏对照参考和已确认差异，核对可见元素及文案都有需求依据。实际检查不同语言、主题、窄屏及状态下的标题与留白、操作可达和内容裁切；结合截图及关键元素边界，不能只凭 document.scrollWidth、DOM存在或构建通过判定布局完整。

## 国际化（i18n）

新增或调整界面、模块默认页面、校验提示或语言格式时，读取[国际化契约](i18n.md)。面向用户的文案使用模块翻译资源，覆盖全屏页、工作台、菜单、按钮、空态、加载状态、可访问名称和页面标题；动态消息使用完整译文与参数，沿用已选库的插值和复数能力。

Mantine 日期控件语言与公开 label 配置、数字和日期时间展示、document.lang 及页面标题跟随应用语言，通过公开接口设置，保持组件原生样式。语言与时区分别管理，展示格式不改变 API 数据格式或已约定的时间语义。

菜单与已显示的错误提示在语言变化后重新解析，切换保留认证会话和表单数据；服务端提供已翻译消息时，按项目契约重新取消息或保留结构化语义再渲染，不能仅更新新产生的提示。按[错误响应国际化](api.md#错误响应国际化)处理后端错误，避免前后端重复翻译。单语言范围也明确 locale，避免页面与控件语言混用。

## 本地时区

用户界面中的时间点默认按用户设备／浏览器的本地时区显示；应用已明确提供用户时区偏好时按该偏好统一展示。语言与时区独立，不能把中文当作北京时间或英文当作UTC，也不能将某个固定偏移当作所有用户的本地时区。

前端负责在展示边界正确解析并转换时间点：后端返回UTC的`Z`或其它有效时区偏移，均表示绝对时间，应转换后展示，而不是截取字符串或写死UTC。接口与缓存保留原始时间语义和字符串；不依赖后端按本机时区返回，也不为显示而改写存储／请求数据。

纯日期`YYYY-MM-DD`不转换时区。不带时区的日期时间不能可靠推断来源时区，必须按接口字段契约处理；契约未定义时记为缺口，不擅自追加`Z`或当作本地时间。数值时间戳须明确秒／毫秒单位。非法值给出适当回退，不能把无效日期当作有效时间展示。

列表、详情、提示和编辑控件对同一时间点保持一致；字段名称不写死“UTC”，除非需求明确为UTC或其它固定业务时区。编辑默认以本地日历时间呈现，在控件边界转换为接口要求的带时区时间点；保留未修改的原始值及既有精度约定，不能因为打开或保存表单改变时间点。遇到夏令时重复／不存在的本地时间，按明确业务规则消歧或校验，不无依据偏移。

审查检查格式化与编辑边界是否硬编码时区、重复转换、混用纯日期与时间点。改动涉及转换时，实际切换至少两个有代表性的浏览器时区，覆盖带`Z`、非零偏移及跨日；有夏令时的适用场景覆盖其边界，验证同一时间点在列表／编辑一致、保存往返不漂移。只在开发机时区截图正常不能判通过；无变化的有效证据可复用。

## API 客户端

采用 Orval + 原生 Fetch + TanStack Query。Huma 导出统一 OpenAPI，Orval 生成 `.redberry/frontend/api.ts`，包含类型、调用函数、query key、Query options 与 hooks。

业务基于 operationId 和类型化参数调用，统一使用 `/api` 同源路径。生成代码直接引用的 React 与 Query 运行依赖由根 `package.json` 显式声明。生成文件不手工修改。

强校验覆盖代码、类型、规范与模块边界；客户端请求和响应不增加重复的 schema 校验。服务端输入校验、表单业务校验和 HTTP 错误处理各自承担职责。

## 列表状态

Router URL 是列表条件的状态来源，页码、每页数量、筛选与排序全部进入 Query 查询键。前端只传递条件，不对当前页再次排序或筛选。

Table 使用服务端模式，开启 `manualPagination`、`manualSorting`，在边界接入[列表响应](api.md#列表查询)：

| 接口字段 | Table 接入 |
| --- | --- |
| `page` | `pageIndex = page - 1`；请求时反向转换 |
| `size` | `pageSize` |
| `items` | `data` |
| `total` | `rowCount` |

修改筛选、排序或每页数量时回到第一页。当前请求对应的服务端响应 `page`、`size` 是最终分页状态，并用于替换 URL；删除后的越界调整交给服务端，前端不根据总数另算页码。

使用 `keepPreviousData` 时，占位数据不参与分页同步，加载期间禁用依赖旧行的操作。

## 表单状态与提交

TanStack Form 是可编辑表单状态的来源，Zod 承担表单业务校验。使用生成类型提交[完整更新](api.md#更新接口)声明的全部可编辑字段，保留 `null`、零值与空字符串的区别。

保存操作放在 TanStack Form 的 `onSubmit`，调用生成请求函数；validator 只负责校验，不执行写入。服务端字段错误通过原生 `setErrorMap({onSubmit: {form, fields}})` 回填，Mantine 从 Field 的错误状态显示错误。

接口层使用 Huma `errors.location` 定位字段，例如 `body.title`。每个表单对已注册字段维护显式、受类型检查的映射；不将任意服务端字符串强断言为字段路径。相同字段的多条错误合并，未映射位置、无字段详情的业务错误与网络失败显示为表单级提示，不丢弃未知位置的错误。

字段通过 `onChange`、`onBlur` 与 Form 校验连接，修正后由原生提交错误生命周期清除该字段的过期错误，不因修改其他字段而清空仍未修正的字段错误。服务端字段错误收到后立即显示，不依赖用户是否先触碰字段。

提交失败回填后继续保持失败语义，不能将 `isSubmitSuccessful` 标记为成功；提交入口消费已显示的失败，避免未处理的 Promise 拒绝。成功提示与成功后的导航仅在成功分支执行；失败后如需复查初始化或权限等服务端状态，保留当前表单、输入及错误再进行后台查询。提交期间锁定本表单输入和保存按钮，避免重复写入及旧响应覆盖新输入。

错误收到后立即显示，并保留到相关输入被纠正、同一操作重试产生新结果或流程确实结束。首次加载与后台刷新分别处理；refetch、重新渲染、缓存失效、自动重试或未修正字段的变化均不能通过卸载表单、重置状态或短暂通知抹掉错误。失败保留可继续使用的输入；秘密值只按既定安全生命周期处理，不写入持久存储。验证“失败 → 状态复查 → 错误及输入仍在 → 定向修改 → 再次提交”的全过程。

非表单操作同样按[错误反馈与诊断](diagnostics.md)处理：查询、后台刷新、上传、下载、流连接和异步任务失败都在对应界面明确显示受影响操作、原因及恢复入口；后台刷新失败可保留旧数据并标明刷新未成功。未知错误位置仍显示操作级反馈，内部故障使用安全说明和关联编号。已显示错误的 Promise 可在入口消费，尚未显示的异常不能仅 `catch` 后忽略或写控制台；避免同一失败被全局和局部提示重复展示。

## 日期控件

日期与时间输入使用同版本的 `@mantine/dates`，由统一 UI 入口提供 `DatePickerInput` 和 `DateTimePicker`，复用 Mantine 主题与 TanStack Form。项目显式声明其 peer 依赖 Day.js，不额外引入表单体系。统一样式入口先加载 core 样式，再加载 dates 样式；日期 locale 等公共设置由 `DatesProvider` 集中维护。

纯日期控件使用字符串或 null，与接口声明的可空性一致，不转换为 Date。时间控件的值为不带时区的日历时间；按[本地时区](#本地时区)默认使用用户本地时间，在控件边界转换为带时区的 RFC 3339 字符串。仅有明确业务要求时使用UTC或其它指定编辑时区；不将控件原值直接当作时间点。

默认 popover 模式以 `onDropdownClose` 标记弹层交互结束；触发器 `onBlur` 仅在未展开时调用字段 `handleBlur`，覆盖直接 Tab 离开的路径。打开日历后的内部焦点移动不提前标记 blur，也不因此显示必填错误。

必填日期清空后暂存为表单空值，提交前由表单校验阻止请求；可空日期保持 `null` 并按接口契约提交。日期与时间字段的服务端错误通过相同的 Form 提交错误槽显示，纠错后按原生生命周期清理。

普通时间编辑开启秒输入。未编辑的时间保留原始接口字符串；编辑后按控件秒精度提交，毫秒为零。必须手工录入毫秒或处理其他业务时区的字段单独明确交互与转换规则。

## 后台页面挂载路径

后台逻辑路由保持模块声明的 `/auth`、`/users` 等路径。挂载前缀只来自 `redberry.yaml` 的 `web.apps.<应用名>.path`：CLI 构建时以 `--base` 传给 Vite 统一资源地址，TanStack Router 的 `basepath` 读取 `import.meta.env.BASE_URL`；不提供环境变量入口，业务不复制前缀拼接器。内部页面导航使用 Router 的 `to`，回跳参数保存不含挂载前缀的逻辑路径；需重载文档时使用 Router 的 `reloadDocument`，品牌首页链接使用相同的 `BASE_URL`。

API 保持 `/api`。单二进制由生成装配携带后台前缀，仅在前缀内回退 SPA，前缀外返回 404，站点根路径可交给独立前端。分离部署的静态服务器采用同样的挂载及回退边界。修改生产前缀须重建，不让构建读取部署运行配置。浏览器测试通过带前缀的 baseURL 和原生相对 URL 访问页面，API 使用 origin 绝对路径。
