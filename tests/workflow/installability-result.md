## 配置与自动装配的边界

应用可以填写外部服务地址、部署秘密和明确的业务策略；可以通过有限 UI 入口定制主题，并选择真正可选的扩展。旧应用升级允许一次接入通用容器。该兼容步骤不能变成每添加一个模块就再写一套模块接线。

模块通过公开入口声明默认能力，生成器连接应用能力。消费者不应复制 API/UI 映射、`XProvider` 包装、模块路由注册、基础设施接线或私有 catalog 项。默认能力必须能在不使用可选扩展的情况下工作；模块不能反向导入应用私有文件或其生成目录。

规范给出的前端装配契约为：

1. 模块可在 `frontend/index.ts` 具名导出 `createProvider(context)`，返回 Provider 组件。
2. CLI 生成 `.redberry/frontend/providers.tsx`，按依赖在外、消费方在内组合。
3. 应用通用入口在 render 外调用 `createModuleProviders(queryClient)`，在 UI 和 Query Provider 内挂载返回的 `ModuleProviders`。
4. context 提供生成 `api`、有限 `ui`、应用 `scope` 和 `queryClient`；模块声明所需最小结构类型，生成调用检查静态兼容性。
5. 无工厂模块透传 children；工厂只定义组件，资源由组件挂载和卸载管理，不在 render 中创建订阅或会话。

这些是当前规范的设计要求，本报告未证明现有生成器已实现。若能力缺失，应由主 agent 在授权范围内推动生成器／模板和模块公开入口修复；不能在示例中补专属胶水后宣称交付。

## 普通菜单页、全屏页与权限

普通模块页面默认进入工作台菜单页；路由 `staticData` 承载 `layout` 和可选 `menu`，后者包含标题与顺序。登录等全屏页面使用 `fullscreen`，不嵌套工作台。页面布局、菜单是否显示和访问控制是三个分别设计、分别验收的行为。

验收应根据已确认范围，分别检查普通模块安装后能否从菜单进入、全屏页面是否脱离工作台、隐藏菜单后的直接 URL 访问是否遵守实际权限约定。全屏页面不会自动获得匿名访问权限，菜单隐藏也不会自动禁止直接访问。

规则有一个待澄清细节：`docs/modules.md:30` 写“layout（默认 workspace 或 fullscreen）”，结合下一句可理解普通页面默认 workspace，但未将默认值与枚举候选清楚分开；`menu` 可选时的默认标题、顺序及隐藏表示也未在已读规范中定义。实施路由生成行为前应补齐这些实际决定，不由验收者擅自发明。此细节不影响拒绝 X 的明确依据。

## 后续派发与收尾

主 agent 修复并完成自检后，每轮启动未参与实现、修复及此前验收的新子 agent，支持时使用 `fork_turns="none"`。交接完整范围与判据、必要规则／Skill 路径、固定源码位置和版本／快照、环境及实际任务入口、允许的测试操作和资源边界，以及原始日志和触发证据。交接不灌输自评、推测根因、推荐修法或预设通过结论。

验收期间主 agent 不并发修改被测源码。内容改变则作废受影响结果并重新交接。验收者可以补测试或复现脚本，不改业务实现、不调低需求、不递归派发。每轮核对完整验收清单，实际运行关键场景；修复后复验原失败、受影响入口及必要回归。不受影响证据可由验收者核实后复用并说明理由。

失败返回入口：记录问题及判据 → 必要排障 → 调研查证与方案判断 → 必要需求／设计／POC → 更新计划 → 编码与自检 → 另一名干净验收者 → 审查。审查引入修改同样重新进入闭环。能力或环境缺失时记录未执行项及恢复条件，不能以主 agent 自检冒充正式独立验收，也不能通过固定轮数、删用例或将必需项改为可选来结束。

正式报告应包含轮次、验收者、源码基准、环境、逐项结果、实际命令与原始证据、复用理由、问题状态及未验项。最终完成声明必须和最后实现一致。
