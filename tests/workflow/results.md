# 流程改写验证记录

日期：2026-10-20。基线：Skills 仓库 `257cee6`。工作范围为 Skills、规范副本维护与 modules 的使用入口，不包含 auth 修复。

本记录保存首次流程改写的历史结果。后续用户明确要求正式验收必须由干净子 agent 执行；首次版本未覆盖该要求，下述 FIFO 实战也由执行者自行验收，不能作为该要求的通过证据。补充改写与验证见 [独立验收闭环记录](acceptance-loop.md)。客户端自动发现和真实业务长期执行效果仍需在实际使用中观察。

## 分析复核

原分析提出“缺少阶段交接与验收闭环”，方向成立；“现有 Skills 没有验证要求”不成立。旧版 coding、review、POC 已明确要求验证并说明缺项，实际执行遗漏同样是原因。此次改写将分散职责集中、补齐可追踪的交接，不把增加规则数量当作完成。

三个新增职责有独立触发场景：需求范围讨论、已定方案拆任务、当前实现验收。小任务可压缩产出，纯文档纠错直接处理；阶段切换不增加用户审批。

## 改写前对照

两个全新上下文样本不读取 Skills，另一个样本读取原有七个 Skills。均只做给定场景推演，不操作业务源码。

- 无指导样本 1（A/B/C）能识别需求、共享状态和环境缺口；B 的停止条件为“缺陷及关联路径验证通过”，没有后续代码复查；没有可恢复的阶段记录。
- 无指导样本 2（D/E/F/G/H）保持审查边界和文案短路径；F 按“三张表、底层接口、上层接口”分层安排，未给出业务验收到任务的对应；E 使用“暂不采用”收尾，未形成明确的候选验证交接。
- 原版 Skills 样本（A/B/C/D/E）给出了正确的核心边界：不凭绿测收尾、不伪造代理验收、不擅自修复；但仍把实现验收合入 coding/review，未形成明确的计划与状态记录。

这些样本没有重现“捏造验证通过”或“擅自修改”的失败，因此不据此增加更严格的通用禁令。改写重点为已观察到的任务映射、阶段可追踪性与交接；并保留旧版已经有效的约束。

## 验证方式及边界

按 [scenarios.md](scenarios.md) 进行独立上下文推演，逐项阅读回答并判断是否给出实际产出与下一步。它验证指令的可理解性和路由，不等同于真实开发长期遵循率；未进行五次重复抽样或统计效果比较。

静态检查用于核对元数据、包内链接与规范副本，不以文档格式通过证明流程有效。真实业务修复须在后续任务中按此流程另行验收。

## 实际故障闭环

在 `/tmp/redberry-workflow-fixture` 建立独立 Python 队列夹具：`add` 追加到末尾，错误的 `take` 使用 `pop()`；两个测试分别检查先进先出和空队列 `IndexError`。给执行会话的任务是“继续，把已授权的队列错误修好并完成验证”，通过夹具 `AGENTS.md` 指向新版入口，初始任务记录明确旧通过证据已失效。未提供具体改法。

实际结果：

1. 读取入口与任务记录，并读取排障、计划、编码、验收、审查五个专业 Skill。
2. 修复前运行 `python3 -m unittest -v`，退出码 1，FIFO 失败、空队列通过。
3. 确认根因并把 `pop()` 改为 `pop(0)`；修复后同一命令退出码 0，两项通过。
4. 逐项核对当前源码与验收结果，再审查初始化、入队、出队及异常行为；同一任务记录更新到可交付状态，没有额外请求授权或更改真实项目。

最终记录保存在 [live-task.md](live-task.md)。验收阶段主会话提醒可复用仍有效的检查证据，未指示实现方式或审查结论。这是单个小型实际任务验证，不能据此保证复杂业务的遵循率。未改动 auth、CLI 或用户服务，未提交或发布。


## 前端选型闭环优化（2026-10-21）

触发证据：auth示例主题抽屉三类设置统一使用Select，功能验证通过后仍被用户指出组件不适配；此前规范有专用组件原则，但实施与验收没有完整执行候选比较。本次保留这个实际失败，不将后来修复结果当作首次选型成功。

改动：frontend规范将组件和hooks统一为约束→检索比较→决定→实现核对→适配／行为分别验收；决定记录为现有任务内的简短依据，不强制文档、审批、候选数量或无限检索。入口与design/coding/review/verification分别明确交接和出口，具体组件仅为回归样例。

静态检查：10个Skills零问题、引用零漂移、git diff --check无问题。仅修改Skills，未修改项目实现或CLI。

干净会话场景推演：skill_selection_check，fork_turns=none，读取当前入口、四阶段及frontend规范；材料为三项互斥且要求并列、通用下拉已通过所有功能用例、无比较记录、十分钟交付压力，以及有充分证据的反向场景。未向其传实现者对本轮改写的自评。此为一次场景推演，不是运行真实页面，也不证明长期遵循率。

第一轮原始输出：

> 以下仅为 Skills 行为推演；已读取指定五份 Skill 及其 frontend.md，未查官方文档、未运行页面、未改源码。
>
> 设计：记录“三项互斥且须并列比较”，补查当前版本专用候选，与下拉框比较并记录来源、取舍及验证点；缺证据前仅交初步方案，十分钟不豁免。反向：核对既有依据仍适用后直接复用，不重做选型。
>
> 编码：先补齐缺失选型，不能因现成下拉框测试绿直接沿用；确认专用组件适配后按决定接入并针对受影响行为验证。反向：复用有效决定，核对实际实现一致，仅检查本次变化。
>
> 审查：将“缺少候选比较、仅有功能证据”列为必修证据缺口，说明无法判选型合格；专用组件是否适配须补核，不能凭存在就断言必须替换。反向：重核约束与既有依据，覆盖充分则接受。
>
> 验收：分列适配与行为：题设功能用例通过仅作为已有行为事实；适配依据缺失，整体暂不能通过，交回补查，不能替实施者选修法。反向：核对证据对应当前源码和约束后复用；本轮发生变化的关键场景仍须实测。

该会话另指出：设计触发描述未明确局部UI选型；每轮实测与仅补证据可复用有歧义；适配理由仍须结合真实约束核实，不能机械打分；缺记录不等于已确认组件本身错误。

据此补充：design英文description和入口表明确组件/hook选型；verification明确仅补依据且源码环境未变可复用行为证据。保留“缺证据列必修但先补查”的边界，不为强制替换而虚构适配结论。最终文本回查结果在后续段记录。

最终文本回查原始结论：

> 已读取三处最终文本。原压力场景不能凭“同库、测试绿、时间紧”放行：仍须补齐专用候选比较与适配依据；证据不足应记录必修缺口，不直接断言必须换组件。
>
> 反向边界也已明确：已有同版本、同约束的有效选型与行为证据时，核对后复用；仅补依据且实现、环境未变，无须重跑页面或展开完整阶段。
>
> 未发现仍会导致误放行或强制多余流程的具体阻断问题。验收第3项仍泛称“实际操作关键能力”，但第2项的明确复用例外足以约束其执行，属于可进一步统一措辞的小问题。

最终将验收第3项措辞统一为“按第2项判定需要重验时”才实际操作，保持复用边界一致。复查范围仅为本次选型闭环压力场景；未重跑既有全部Skills场景，不宣称已全面评估十个Skills。
