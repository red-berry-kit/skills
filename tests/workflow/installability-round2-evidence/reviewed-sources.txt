### README.md
1: # Red Plum Skills
2: 
3: 统一入口：[using-redplum](using-redplum/SKILL.md)。它负责选择阶段、恢复任务与组织交付；各专业 Skill 定义阶段的输入、执行、出口和下一步。阶段路径与发现问题后的调研、修复循环只在入口维护；正式验收的干净子 agent、交接材料和证据规则由 [redplum-verification](redplum-verification/SKILL.md) 定义。
4: 
5: ## 在项目中使用
6: 
7: 将需要的 Skill 目录安装到客户端支持的位置。建议安装整套，以便入口串联各阶段；也可单独使用某个专业 Skill。每个包内的相对资料链接可以独立解析；专业 Skill 的名称引用表示阶段交接，不代表下游已经安装或执行。
8: 
9: 项目 `AGENTS.md` 保留以下入口即可，其余位置继续维护项目特有规则：
10: 
11: > Red Plum 的需求、调研、设计、实现、排障、验收与审查使用已安装的 `using-redplum`；按入口实际读取所需专业 Skill，并维护当前阶段、产出、证据与下一步。复用已有授权及有效结论。
12: 
13: 安装方式依客户端而定，安装后核对实际文件路径与发现结果；源码更新不保证当前会话重新加载目录。Skills 由开发者安装和更新，Red Plum CLI 不管理 Skills。
14: 
15: ## 维护
16: 
17: - `<skill-name>/SKILL.md`：流程源文件。`description` 用英文描述触发条件，正文中文。
18: - `docs/`：随包技术规范的唯一维护源，自独立仓库已有规范快照迁入。项目本身的规则优先；不要再用旧模板仓库的打包脚本覆盖本仓库。
19: - `<skill-name>/references/`：规范副本。现有七个 Skill 保留独立安装所需资料；自包含的需求、计划、验收 Skill 无需复制这些资料。
20: - `tests/workflow/`：行为验收场景和本次验证结果；不作为项目开发时的必读文件。
21: 
22: 规范变更后，在本仓库执行：
23: 
24: ```bash
25: python3 scripts/sync-references.py
26: python3 scripts/sync-references.py --check
27: python3 scripts/check-skills.py
28: ```
29: 
30: 流程变更应先看实际失败或对照行为，再逐项修改并运行独立场景验收。静态检查验证元数据、名称引用及包内 Markdown 链接；它不证明执行者会持续遵守流程。每次测试区分推演、真实执行及未验证内容，记录实际限制。


### using-redplum/SKILL.md
1: ---
2: name: using-redplum
3: description: Use when starting or continuing requirements, research, design, implementation, debugging, verification, or code review in a Red Plum project.
4: ---
5: 
6: # 红梅开发入口
7: 
8: 负责选择阶段、检查交接和汇总交付。先读取目标项目的 `AGENTS.md`、相关实现和本任务已有记录；项目规则优先，配套规范按需从[开发约定](references/conventions.md)进入。
9: 
10: ## 建立或恢复任务
11: 
12: 在已有任务记录中维护：**目标与范围、验收条件、当前阶段、已有产出及证据、缺项、下一步**。短任务可直接在对话中记录；跨轮次或多阶段任务复用项目已有计划或过程文档，不要求每阶段新建文件。继续任务时核对记录与当前源码，复用仍适用的结论。
13: 
14: 开始时简述当前阶段及将使用的 Skill。进入阶段前实际读取对应 `SKILL.md`，同一上下文中已读且未变化的内容可复用。通过客户端可用机制发现或调用，不能调用时直接读取安装文件。只有名称或描述不算执行；每次交接更新产出、证据和下一步。
15: 
16: ## 选择路径
17: 
18: | 触发条件 | 阶段与 Skill | 进入下一阶段的依据 |
19: | --- | --- | --- |
20: | 新需求、范围变化、验收语义不清 | 需求：`redplum-requirements` | 可观察的验收条件，决策缺口已明确 |
21: | 影响决策的技术事实未知，或验收／审查发现问题需要选择修复方案 | 调研：`redplum-research` | 来源、方案比较、适用条件及待实测问题 |
22: | 职责、接口、状态或依赖关系需要决定 | 设计：`redplum-design` | 行为与边界方案能对应验收条件 |
23: | 关键可行性必须实测才能定案 | 风险验证：`redplum-proof-of-concept` | 候选的实测结果返回设计定案 |
24: | 方案可实施，需要拆解或重排任务 | 计划：`redplum-planning` | 任务、依赖、验收及验证对应 |
25: | 实施已明确的变更 | 编码：`redplum-coding` | 实现、生成结果和局部检查证据 |
26: | 实现完成或用户要求验收 | 验收：`redplum-verification` | 干净子 agent 对当前实现的逐项结果及缺项 |
27: | 用户要求审查或实现准备交付 | 审查：`redplum-code-review` | 范围明确的审查结论及问题处置 |
28: | 出现异常、失败或回归 | 排障：`redplum-debugging` | 根因证据和修复边界，交回实施 |
29: 
30: 实现任务通常按“需求 → 必要调研／设计／POC → 计划 → 编码 → 验收 → 审查 → 交付”推进。阶段是否展开由上表的条件决定：
31: 
32: - 需求与设计已明确：引用已有产出，直接计划；局部修改可用一句话说明改动、验收和验证方式。
33: - 故障修复：排障 → 必要的需求或设计调整 → 计划 → 编码 → 验收 → 审查。已证实的审查问题复用证据，无需重复诊断。
34: - 仅需求、调研、设计、计划或审查：在用户指定的阶段交付，不自动扩大为实现。
35: - 纯说明、简单查询、文档纠错：直接处理并核对结果，不展开软件实施流程。
36: 
37: 已有授权范围内，交接完成后继续推进，不把阶段切换变成确认请求。影响结果且无法查明的用户选择才需要澄清；等待时继续独立工作。所需 Skill 缺失时先查找安装来源，明确缺失及替代依据；可继续不依赖该缺口的工作，不声称执行了缺失的 Skill。
38: 
39: ## 独立验收与修复闭环
40: 
41: 正式实现验收必须由新的干净上下文子 agent 执行；每次修复后另启一位，不复用实现者或上一轮验收者。派发方式、材料边界和证据要求以 `redplum-verification` 为准。主 agent 组织交接与修复，编码自检不能替代独立验收。
42: 
43: 验收或审查发现问题后，在已有修复授权内持续执行：
44: 
45: 1. 记录问题编号、对应判据、触发与证据；根因不清时交 `redplum-debugging`，已确认的根因直接复用。
46: 2. 交 `redplum-research` 查证并比较适合当前约束的修复方案。已有有效依据可复用，但仍记录选择理由；修法看似明确也不能省掉这项判断。
47: 3. 按需回需求、设计或 POC，更新计划，由 `redplum-coding` 修复并自检。
48: 4. 将当前实现交新的干净子 agent 验收；它核对完整验收清单，执行本轮受影响项及必要回归，不能只复查上一条缺陷。通过后完成代码审查；审查又发现问题则返回本闭环。
49: 
50: 轮次、验收者、源码基准、问题处置及证据维护在同一任务记录中。只有**完整必需验收项全部通过、必修问题关闭、审查完成且证据对应最终实现**，才能交付完成；不以固定轮数或暂时没有新发现作为通过条件。完善标准指约定范围内可观察的行为、边界和失败场景，不是无限添加功能或保证零缺陷。发现范围内判据遗漏先补齐，不能通过删用例、降低标准或把必验项改为可选来收尾。
51: 
52: 环境、权限或子 agent 能力不足时继续不受阻的工作，记录未完成项与恢复条件，不以主 agent 自验冒充独立验收。用户只要求验收或审查时交付发现与建议，修复须有授权；显式暂停或范围调整按用户要求执行。
53: 
54: 交付时报告实际改动、独立验收轮次与证据、问题关闭情况和未验证项。必需项缺失只能标记“部分完成／受阻”；POC、测试数量或构建成功不能替代正式验收。提交、发布及外部操作仍遵循本任务授权。


### redplum-requirements/SKILL.md
1: ---
2: name: redplum-requirements
3: description: Use when a Red Plum feature needs requirements clarified, its scope changes, or its acceptance criteria and failure behavior are incomplete.
4: ---
5: 
6: # 红梅需求澄清
7: 
8: 把用户目标转为可验收行为。输入为用户请求、现有实现、项目约束和已确认决定；已明确的内容直接复用。流程由 `using-redplum` 组织；单独调用时交付需求结果，不擅自进入实现。
9: 
10: ## 执行
11: 
12: 1. 还原目标：谁在什么条件下做什么，期望看到什么结果。检查已有能力和约束，区分本次范围、明确不做的内容及未决项。
13: 2. 按用户操作梳理正常、失败和恢复行为。涉及共享状态时列出相关操作及其顺序或并发约束；只展开本次实际受影响的链路，不增加未经要求的功能。
14: 3. 可复用模块将“干净应用通过 CLI 添加并配置后使用默认能力”纳入范围，区分必要配置、业务策略与不应由使用者编写的装配。将每个范围内要求写成可观察判据：**前置条件／动作或事件／预期结果**，包括与任务相关的错误和边界。沿用项目编号或简短标签，便于计划、验收及审查引用。
15: 4. 分开标记已确认要求、可验证假设和待用户决定事项。技术事实交 `redplum-research` 查证；无法从上下文查明且会改变结果的业务选择才询问用户。已有批准继续有效，只补新增缺口。
16: 
17: ## 出口与交接
18: 
19: 交付目标、范围、逐项验收条件和未决项，并更新当前任务记录。示例判据：“导出任务执行失败后，列表显示失败状态；刷新页面后仍能看到该状态。”不能用“可靠、全面、行业标杆”代替判据。
20: 
21: 关键行为已明确时交 `redplum-design`；既有方案可直接复用时交 `redplum-planning`。仍有未知项时指出它阻断哪个决定，推进不依赖它的部分。需求讨论结束只表示需求阶段完成，不表示实现已交付。


### redplum-design/SKILL.md
1: ---
2: name: redplum-design
3: description: Use when a Red Plum change needs decisions about architecture, module responsibilities, public interfaces, state transitions, dependencies, or abstractions.
4: ---
5: 
6: # 红梅设计
7: 
8: 输入为已明确需求、验收条件、现有架构和调研证据。形成可实施的行为方案；流程由 `using-redplum` 组织。项目规则优先，涉及模块协作时读取[模块与依赖](references/modules.md)。
9: 
10: ## 执行
11: 
12: 1. 核对需求与技术事实。业务选择缺口交 `redplum-requirements`，技术事实缺口交 `redplum-research`；已有且仍适用的决定直接复用。
13: 2. 划分职责、公开接口和依赖方向。可复用模块按[添加即用的交付契约](references/modules.md#添加即用的交付契约)设计默认装配，列清必要配置与可选扩展，不能以示例手工接线代替默认能力。说明调用方必须知道的输入、输出、错误与不变量，优先简单直接的方案；新增抽象须对应实际变化点及收益。
14: 3. 沿操作及数据流设计关键行为。涉及共享状态时列出所有受影响的读写入口，说明状态迁移、资源生命周期及必要的事务、并发与副作用边界；覆盖失败、取消或恢复中本次实际需要的行为。
15: 4. 将方案行为对应到验收条件。给出关键取舍、受影响模块、兼容或迁移影响和待验假设。可行性必须实测时，明确候选与通过判据，交 `redplum-proof-of-concept`，结果返回本阶段定案。
16: 
17: ## 出口与交接
18: 
19: 交付：**职责与接口、关键行为与不变量、验收对应、取舍及限制**，更新同一任务记录。关键决定有依据、范围内行为有验证去向时交 `redplum-planning`；有阻断项则标记初步方案并说明所需证据。
20: 
21: 局部修改沿用既有方案时，直接说明局部改法及影响，无需额外设计文档或审批。只要求设计时在方案交付后停止。主文档保留最终有效规则，调研与实验材料留在项目过程资料区；方案已定不代表代码已经实现。


### redplum-planning/SKILL.md
1: ---
2: name: redplum-planning
3: description: Use when an agreed Red Plum change needs an implementation plan, dependency ordering, acceptance mapping, or replanning after new findings.
4: ---
5: 
6: # 红梅实施计划
7: 
8: 输入为验收条件、已定方案、现有实现和验证条件。将范围拆为可独立判断结果的工作单元。已有计划有效时直接复用；流程由 `using-redplum` 组织。
9: 
10: ## 执行
11: 
12: 1. 核对关键行为已明确、关键可行性已有依据。业务语义缺口交 `redplum-requirements`，设计缺口交 `redplum-design`；仅规划不依赖未决项的部分。
13: 2. 沿完整业务链拆任务，列出源码、调用方、生成输入及接入位置。每项记录：**目标行为／依赖／改动范围／对应验收条件／验证方式**。基础设施任务注明为哪条业务链提供能力，避免只列“后端、前端、测试”而无法验收。
14: 3. 根据依赖排序，提前核实测试入口、所需服务和环境。与状态或资源共享有关的变更，列出受影响操作与要保持的不变量；为这些操作安排验证，不能只覆盖报错的那个入口。
15: 4. 可复用模块安排干净消费应用的真实 CLI 安装与核心操作验收，将生成器／模板的缺口纳入对应任务，不能只验证已经接线的示例。将必要的生成、示例同步、迁移或配置调整、干净子 agent 正式验收及代码审查纳入安排，按 `redplum-verification` 准备独立验收的材料与环境。命令以目标项目实际定义为准；环境缺口注明影响与可行替代范围，不用替代环境抹去必验项。
16: 
17: ## 出口与交接
18: 
19: 每条验收条件均有实施任务和验证去向，每个任务的前置依赖可判断，未决事项没有被写成已完成。将计划更新到同一任务记录，交 `redplum-coding` 逐项执行；已获授权且条件满足时直接继续。
20: 
21: 局部修复可压缩为一行：“修复某调用的过期结果提交；覆盖共享写入入口；以乱序复现与相关回归验收。”无需固定任务数量或新增计划文档。只要求计划时，交付计划及缺项，不开始编码。


### redplum-coding/SKILL.md
1: ---
2: name: redplum-coding
3: description: Use when implementing or refactoring an agreed Red Plum change, integrating generated clients, or applying an authorized bug fix.
4: ---
5: 
6: # 红梅编码
7: 
8: 输入为已明确需求、方案和实施安排。缺少关键行为或任务映射时分别交 `redplum-requirements`、`redplum-design` 或 `redplum-planning` 补齐；局部变更可直接引用已有约定。流程由 `using-redplum` 组织。
9: 
10: ## 执行
11: 
12: 1. 确认源码归属与生成边界。以目标项目规则为准，按范围读取[开发约定](references/conventions.md)、[模块与依赖](references/modules.md)、[API 契约](references/api.md)或[前端开发](references/frontend.md)。邻近风格与语言惯例优先，跨模块通过公开入口协作。
13: 2. 按计划小步实现完整行为，保留验收对应。故障修复先确认失败判据，再修改根因；新行为按风险建立可观察的回归验证。共享逻辑修改追踪调用方，超出既定接口或状态方案时返回设计。
14: 3. 可复用模块实现[默认装配](references/modules.md#添加即用的交付契约)，不向消费应用复制模块专属接线来掩盖生成能力缺失。生成产物的修复落在源码、生成输入或官方配置，再执行项目现有生成入口并核对差异。同步验证副本遵循项目机制，不把副本当源码修改。迁移、配置与版本变化按项目规则处理。
15: 4. 从实际脚本或工具帮助中选择命令，执行项目必需的格式、静态、编译及独立类型检查，运行本次行为与边界的相关测试。构建与测试不能替代独立类型检查；已有有效证据可复用。
16: 5. 记录改动、实际检查结果、失败和未执行项，核对需求未被实现细节缩小。修改受影响文档的最终规则；实验与过程证据留在已有过程资料区。
17: 
18: ## 出口与交接
19: 
20: 实现与生成产物一致、局部检查已有证据后，更新任务记录，由主 agent 按 `redplum-verification` 派发干净子 agent 做正式验收，再交审查。提供源码与原始自检证据，不替验收者预填通过结论。编码完成不等于整体任务完成。遇到失败进入 `redplum-debugging`，修复后回到原验收条件；来自验收或审查的问题按 `using-redplum` 闭环处理。必需检查受阻时明确阻断并继续独立工作。
21: 
22: 低风险文案或等价局部修改核对实际差异及适当现有检查，无需新增镜像实现的测试。只交付计划、代码草案或未执行的验证安排时，按实际状态说明，不报告为已运行通过。


### redplum-verification/SKILL.md
1: ---
2: name: redplum-verification
3: description: Use when a Red Plum implementation needs acceptance testing, completion evidence, integration checks, or reassessment after a fix or environment change.
4: ---
5: 
6: # 红梅实现验收
7: 
8: 验证当前实现是否满足约定行为。输入为验收条件、实施范围、当前源码与环境、原始检查证据。可独立用于已有实现；整体流程及修复闭环由 `using-redplum` 组织。代码审查检查实现与风险，验收检查可观察行为和证据，两者互相补充。
9: 
10: ## 干净验收者与交接
11: 
12: 主 agent 每轮新建一位未参与实现、修复或先前验收的子 agent，关闭会话继承；支持 `fork_turns` 时使用 `"none"`，其他客户端使用等效独立会话。只切换角色称呼、压缩实现对话或让旧 agent 清空记忆，不构成干净上下文。已被派发的干净验收者直接执行本阶段，不递归派发验收者。
13: 
14: 交接材料包含：用户确认的范围与完整判据、项目规则和必要 Skill 路径、当前源码位置及版本／快照、运行环境和实际任务入口、允许的测试操作与资源边界。提供原始日志及问题的触发、复现证据供核实，不灌输实现者的自评、推测根因、推荐修法或预设通过结论；验收者先独立核对完整范围，再核实历史问题。实现过程记录不是必读材料。
15: 
16: 验收者实际读取本 Skill 和必要规则，独立选择并执行检查，报告事实和缺项。可在隔离范围补充测试、复现脚本和证据；不修业务实现、调整需求或替实现者选定修法。验收期间固定被测源码，主 agent 不并发修改；内容变化时作废受影响结果并重新交接。无法创建独立上下文时如实报告能力缺口，已有自检仅作为自检证据。
17: 
18: ## 执行
19: 
20: 1. 建立对应表：**验收条件／实际入口与场景／验证方式／结果／证据**。结果区分通过、失败、未执行及有理由的不适用。先核对范围完整性，再判断结果；缺少判据时返回需求阶段，不能按现有测试反向缩小需求。
21: 2. 核对已有原始证据对应的源码、配置、依赖、环境和用例，由验收者决定哪些不受影响的检查可复用并写明理由。每轮实际执行关键验收场景；修复后必须重验原失败、受影响部分和必要回归。实现者的“全部通过”摘要不构成验收证据。构建、类型检查、局部测试、POC 和生产环境验证分别说明范围，不能相互替代。
22: 3. 从项目实际任务入口执行必需检查及风险相关测试。可复用模块必须在干净应用通过真实 CLI 添加，只填必要配置即可运行核心能力；记录人工改动，API 映射、Provider 等模块专属接线不能算配置。已有 examples 不能替代安装验收；本地来源或隔离版本夹具注明覆盖范围。验证用户操作到最终状态的真实调用链；涉及共享机制时，检查所有受影响入口是否有验收覆盖。按变化选择失败、恢复、并发或持久化场景，不机械要求每类任务都做全套测试。
23: 4. 对失败、覆盖缺口或可疑结果记录编号、对应判据、预期与实际、复现条件和原始证据，交回主 agent 按 `using-redplum` 的调研与修复闭环处理。验收者不边修边宣告通过；测试修订必须保持业务判据，不能删除失败用例或降低约定来获得绿色结果。
24: 5. 环境不足时先检查已有配置能否提供不干扰用户服务的独立验证方式。可用替代环境只证明其范围；记录仍缺的条件、受影响验收项与恢复步骤。只清理本次创建的资源。
25: 
26: ## 出口与交接
27: 
28: 输出**轮次与验收者标识、源码基准、环境、逐项验收表、实际命令及结果、证据位置、复用依据、问题与未验项**，交回主 agent 更新同一任务记录。必需项全部通过才标记本轮验收完成，交 `redplum-code-review`；本轮检查已通过且无新增变化时不重复运行。
29: 
30: 必需项失败或未执行时标记部分完成，继续可执行工作。若用户只要求验收，则以验收报告收尾，不自动修复或发布。示例结论：“本地真实 API 链路通过；目标代理环境未提供，代理验收未执行，暂不能判定该部署形式通过。”


### redplum-code-review/SKILL.md
1: ---
2: name: redplum-code-review
3: description: Use when reviewing Red Plum code for requirement compliance, design issues, project conventions, verification gaps, or regressions after fixes.
4: ---
5: 
6: # 红梅代码审查
7: 
8: 输入为需求、已定方案、变更范围、当前源码与验证证据。围绕可定位的实际问题审查；流程由 `using-redplum` 组织，规范按需从[开发约定](references/conventions.md)进入。
9: 
10: ## 执行
11: 
12: 1. 固定审查对象。使用可用的 Git 基点与工作区变更，包含新增及未跟踪文件；无 Git 或历史基线时，以文件清单和当前内容固定范围，说明无法判定的历史差异，不因此放弃当前源码审查。
13: 2. 对照需求和方案追踪输入、调用、状态与结果。检查受影响的模块职责、公开接口、依赖、不变量及失败行为。共享机制变更检查相关调用入口，复查也覆盖修复新影响的行为，不能只看补丁行。
14: 3. 核对项目规则与生成边界，复用工具已有结果。个人偏好作为可选建议；未查明的风险作为待核实项，不当作已确认缺陷。
15: 4. 核对验收条件与证据范围。可复用模块对照[添加即用的交付契约](references/modules.md#添加即用的交付契约)，检查默认装配及干净消费应用的 CLI 安装证据；专属接线藏在 examples 中仍是交付缺陷。检查源码、环境和用例是否匹配，识别缺失场景及失败。必要时执行针对性复现；实际结果属于哪个范围就报告哪个范围，测试数量不构成覆盖证明。
16: 5. 按影响排序报告问题，每项附**位置、触发条件、影响、证据、修复或复查方向**。复用原问题清单记录已修、仍存或待验，避免重复报同一根因。
17: 
18: ## 出口与交接
19: 
20: 输出审查范围、问题及处置状态、实际检查和验证限制，更新同一任务记录。没有发现问题时也说明覆盖边界，不给出全面正确性保证。
21: 
22: 仅审查任务在报告处收尾，不修改源码。已有修复授权时，将问题交回 `using-redplum` 的调研与修复闭环；修复后按 `redplum-verification` 重新安排干净子 agent 验收，再回本阶段复查，保持同一任务的问题记录。审查意见不能替代行为验收，审查发现的修改同样会影响旧验收证据。实现任务满足入口规定的完成条件后汇总交付，缺项明确保留。


### redplum-research/SKILL.md
1: ---
2: name: redplum-research
3: description: Use when a Red Plum decision depends on technical facts, existing solutions, library behavior, dependency maintenance, technology suitability, or a remedy for an acceptance or review finding.
4: ---
5: 
6: # 红梅调研
7: 
8: 输入为待回答的问题、需求约束、目标版本与已有证据。输出支持当前决策的依据；需求范围和业务选择由 `redplum-requirements` 处理，流程由 `using-redplum` 组织。
9: 
10: ## 执行
11: 
12: 1. 阅读相关实现、已定方案和历史实验，明确问题及决策标准。旧结论先核对版本、环境和范围，仍适用时复用。
13: 2. 按项目约定使用文档与检索工具，优先官方文档、对应版本源码、发布记录，再结合实际采用案例。关键事实附具体来源和适用条件；来源冲突或资料缺失明确保留，不用宣传、星数或版本号替代适配证据。
14: 3. 比较候选与现有能力，考虑需求匹配、维护状态、接入及运维成本。分别标记来源事实、项目推断和待实测假设；资料未说明某能力，只能判定证据不足。
15: 4. 对必须实测的问题，给出候选、目标环境、最小真实接入范围及通过/失败判据。没有条件执行时保留缺项，不把待验推荐升级为最终选型。
16: 
17: ## 验收与审查问题的方案选择
18: 
19: 逐项关联问题编号、根因证据和不可降低的验收判据。比较最小根因修复与其他合理方案，依据正确性、安全边界、兼容性、维护和运维成本选择当前项目最合适的方案，记录取舍与回归验证去向；不把“最新”“流行”或“改动最少”单独当成最佳依据。
20: 
21: 调研深度与不确定性匹配：本地源码、规范和复现足以确定的机械性修复，可用这些证据简短说明唯一合理方案，无需虚构多个候选或机械联网；依赖库、协议或外部行业实践的判断必须查对应权威来源。已有依据适用时引用并复核；证据不足先保留假设，必要时交 POC，不能把猜测直接作为修复方案。
22: 
23: ## 出口与交接
24: 
25: 交付：**问题的答案与状态、来源及适用条件、未决问题与验证去向**，更新同一任务记录。证据足以支持当前决定时结束调研；资料受限时说明缺失证据阻断哪个决定，继续可独立查证的部分。
26: 
27: 新方案交 `redplum-design`；初步设计已有、关键适配需实测时交 `redplum-proof-of-concept`，实测后返回设计定案。只要求查询或调研时在本阶段收尾，报告范围清楚即可，不自动安装依赖或实施方案。
28: 
29: 复用型材料存入项目已有过程资料区；主方案仅写最终有效规则。参考规范按需阅读[开发约定](references/conventions.md)。


### redplum-debugging/SKILL.md
1: ---
2: name: redplum-debugging
3: description: Use when a Red Plum project has errors, unexpected behavior, failing tests, performance regressions, or intermittent failures requiring root-cause analysis.
4: ---
5: 
6: # 红梅排障
7: 
8: 输入为预期与实际行为、问题证据和当前实现。定位根因并确定修复边界，再交编码、验收与审查闭环；整体流程由 `using-redplum` 组织，技术约束按需读取[开发约定](references/conventions.md)。
9: 
10: ## 执行
11: 
12: 1. 固定现象与环境：触发条件、输入、时间顺序及影响，区分用户反馈、实际观测与解释假设。已证实的审查问题复用原证据，不重做无关调查。
13: 2. 建立失败判据。优先最小可重复场景或测试，确认失败对应原问题并保留结果。无法复现时收集必要日志、请求与上下文；明确缺少的条件，不靠试改把猜测当成根因。
14: 3. 沿实际数据流验证假设，每次检查一个关键因素。涉及共享状态、资源或公共机制时追踪其他读写入口，确定同类触发与受影响的不变量。库行为未知时交 `redplum-research` 查证。
15: 4. 形成最小修复方案，说明根因、修复位置、相关入口及回归场景。需要改变约定行为或模块接口时，分别交需求或设计阶段；不附带无关重构。
16: 
17: ## 出口与交接
18: 
19: 交付：**现象、失败判据与证据、已确认根因／待验证假设、修复范围、回归判据**，更新同一任务记录。验收或审查问题定位后交 `redplum-research` 形成方案依据，遵循 `using-redplum` 的闭环；已有调研证据有效时复用。其他故障在根因与修复方案明确且已获授权后，交 `redplum-planning` 安排工作（小修复可简写），再由 `redplum-coding` 实施、`redplum-verification` 独立验收、`redplum-code-review` 复查。
20: 
21: 原失败消失之外，还要核对受影响行为及必需检查；最小复现通过仅证明其范围。证据不足时继续取证，报告阻断与恢复条件。用户仅要求诊断时交付诊断结论，不自动改代码；用户已授权修复时，不因阶段切换重复询问。


### redplum-proof-of-concept/SKILL.md
1: ---
2: name: redplum-proof-of-concept
3: description: Use when a preliminary Red Plum design or technology choice needs practical integration evidence, or when reviewing whether a POC meets its criteria.
4: ---
5: 
6: # 红梅可行性验证
7: 
8: 输入为初步方案、候选及版本、目标环境、真实使用场景和通过判据。验证关键可行性，结果返回设计定案；正式实现另交 `redplum-verification` 验收。流程由 `using-redplum` 组织。
9: 
10: ## 执行
11: 
12: 1. 固定待证明的问题与必验项。没有初步方案时交 `redplum-design`；事实未知时交 `redplum-research`。核对历史结果的版本、环境和用例后决定复用范围。
13: 2. 在项目已有实验区搭建最小真实接入，固定依赖与必要锁文件。按问题覆盖所需的模块、存储或前后端链路；协议夹具和孤立示例只证明各自范围。
14: 3. 运行对应生成、编译、类型及静态检查和场景验证。逐项记录通过、失败、未执行及证据，不用单项通过概括全部可行。
15: 4. 保留失败结果，分析配置、版本、接入方式或候选本身；修正后复验受影响部分。生成代码问题修在源码、生成输入或官方配置；检查标准与验收范围的变化须有明确依据，不能为过关降低标准。
16: 5. 只清理本次创建的资源，保留复现步骤、必要实验代码及结果。环境缺失时说明能验证的范围和阻断，不把计划执行记为已执行。
17: 
18: ## 出口与交接
19: 
20: 输出：**候选与环境、逐项判据及结果、复现证据、适用限制、定案建议**，更新同一任务记录。必验项全部通过后才给出该范围的可行结论，交 `redplum-design` 定案，再进入计划；失败或缺项则保持初步方案状态，给出调整或补验去向。
21: 
22: 只评阅已有实验时说明没有重跑。只要求 POC 时在实验报告收尾。最终主方案保留有效决定，实验与失败材料放过程资料区。项目技术约束按需从[开发约定](references/conventions.md)查阅。


### docs/status.md
1: # 规范与实现归属
2: 
3: 本仓库维护十个 Red Plum Skills、配套技术规范及流程行为测试。`docs/` 是规范唯一源；七个需要参考资料的 Skill 通过同步脚本获得 `references/` 副本，需求、计划、验收三个 Skill 自包含。Skills 由开发者独立安装与更新，CLI 不管理。
4: 
5: ## 工程边界
6: 
7: - `red-plum-kit/skills`：阶段入口、交接与验收闭环、随包技术规范。
8: - `red-plum-kit/cli`：CLI、应用及模块模板、工作区与生成装配、工程任务编排。
9: - `go-admin-template`：公共运行时 `app`、`config`、`migrate` 与运行库自身检查。
10: - 消费项目：业务、配置、模块接入、部署和实际验收证据。
11: 
12: 规范描述约定，不代表所有旧版本已经具备这些能力。执行任务前核对目标项目实际源码、CLI／模板版本及任务入口；模块默认装配的缺口按[模块交付契约](modules.md#添加即用的交付契约)处理。
13: 
14: ## 检查与证据
15: 
16: Skills 仓库使用 `python3 scripts/check-skills.py` 检查元数据、名称引用与包内链接，使用 `python3 scripts/sync-references.py --check` 检查规范副本；变更规范后先执行不带 `--check` 的同步命令。行为场景与报告在 `tests/workflow/`，静态检查不能证明流程行为或业务模块可用。
17: 
18: 其他工程的 `check/test/build` 等任务以各自 AGENTS、脚本或实际工具帮助为准，不把运行库的 Taskfile 当成 Skills 仓库入口。软件交付是否完成，以对应当前源码、环境和完整判据的独立验收及审查证据为准；实验、模拟和已有示例不能代替实际安装验收。远程 CI、正式版本发布和目标部署没有执行时必须保留缺项。


### docs/modules.md
1: # 模块与依赖
2: 
3: 用户业务与基础功能都作为独立模块维护。`redplum create mod` 使用模块模板创建完整的前后端基础文件；配置定义与迁移按需添加。自有源码放项目内的模块目录，外部源码由 CLI 管理于 `.redplum/modules/`。
4: 
5: ## 公开入口
6: 
7: | 部分 | 文件 | 导出约定 |
8: | --- | --- | --- |
9: | 后端 | `backend/module.go` | 导出 `Module`，统一提供 Fx 装配 |
10: | 前端 | `frontend/index.ts` | 使用具名导出，公开允许外部使用的内容 |
11: 
12: 跨模块调用通过后端的 `backend` 包或前端的 `frontend/index.ts`，不直接引用内部实现。Go 的包导出规则仍然适用；`module.go` 是装配入口文件，不意味着 Go 可以限制其他包只访问这一文件。
13: 
14: 描述文件不重复声明入口。CLI 根据约定路径生成装配代码。
15: 
16: 跨模块引用包含类型引用，模块内部可引用自身实现。私有子目录的 `index.ts` 不自动获得模块级入口地位；提供方不能通过公开入口转出其他模块的私有实现。
17: 
18: 边界检查按真实文件归属判断，覆盖相对路径、tsconfig 别名、软链接与再导出。动态导入使用固定字面量。模块根由依赖管理器持有的模块图提供，业务不另维护边界清单。
19: 
20: ## 添加即用的交付契约
21: 
22: 可复用模块必须在干净应用中通过 CLI 添加并填写必要配置后，直接使用其默认能力。必要配置包括外部地址、部署秘密和明确的业务策略；不包括让使用者复制示例中的 API 映射、Provider、路由注册或基础设施接线。
23: 
24: 设计时分清模块默认装配、应用配置和可选扩展。模块通过公开入口声明默认装配；生成器连接应用能力，模块不得反向引用应用私有文件或其生成目录。扩展接口不能成为默认路径必须手写的步骤。缺少通用装配能力时，修复生成器／模板的契约，不在每个消费应用重复补胶水代码。
25: 
26: 验收至少有一条独立消费链：新建应用 → 真实 CLI 添加模块 → 必要配置 → 启动 → 模块核心操作；检查生成客户端、路由、配置、迁移及适用的卸载／恢复行为。记录所有人工改动，出现模块专属接线即判定默认接入未完成。已有 examples 的业务测试只能补充这条证据。未发布模块可使用 CLI 支持的本地来源或隔离的版本仓库夹具，注明所覆盖的安装路径，不能以复制源码或手改生成产物替代安装。
27: 
28: 前端模块可在 `frontend/index.ts` 具名导出 `createProvider(context)`，返回 Provider 组件。CLI 生成 `.redplum/frontend/providers.tsx`，按依赖在外、消费方在内组合；应用入口在 render 外调用 `createModuleProviders(queryClient)`，在 UI 与 Query Provider 内统一挂载返回的 `ModuleProviders`。上下文提供生成 `api`、有限 `ui`、应用 `scope` 和 `queryClient`；模块用最小结构类型声明所需能力，生成调用负责静态兼容检查。无工厂的模块直接透传 children。工厂只定义组件，不获取资源；组件挂载／卸载管理资源，不在 render 中创建订阅或会话。应用主题可通过有限 UI 入口定制，旧应用升级需一次接入通用容器，不为每个模块增加专属装配。
29: 
30: 前端页面在路由 `staticData` 中声明 `layout`（省略时为 `workspace`，全屏需显式设为 `fullscreen`）及可选 `menu`（必填标题 `title`、可选顺序 `order`，省略顺序为 0，同序沿用路由装配顺序）。模块模板为普通页面生成菜单声明；未声明 `menu` 的页面不进入菜单，全屏页面也不进入工作台菜单。登录等全屏页不嵌套工作台。布局、菜单可见性与访问控制分别设计和验收，不把全屏或隐藏菜单当成权限声明。
31: 
32: 模块专有 npm 依赖自行声明可解析的版本；只有平台已经提供的共同依赖才引用统一 catalog，不要求每个消费应用补模块私有 catalog 条目。
33: 
34: ## 装配与生命周期
35: 
36: 使用 Uber Fx 组合模块，通过构造函数参数表达依赖。容器操作集中在 `backend/module.go` 与项目装配层，业务代码通过显式参数获取依赖。
37: 
38: 统一检查入口执行 `fx.ValidateApp`，在不执行构造器的情况下检查依赖缺失、重复提供与循环依赖。图检查使用类型化提供者，不要求加载部署配置；它属于检查阶段的图验证，不是 Go 编译期验证。
39: 
40: 构造阶段只创建对象和注册生命周期。数据库连接、端口监听等资源在 `OnStart` 获取，通过 `OnStop` 逆序释放；某个启动步骤失败时，该步骤负责清理自身获取的资源，Fx 回退已成功启动的步骤。构造器业务错误与实际启动行为通过测试验证。
41: 
42: ## 模块描述
43: 
44: `redplum.yaml` 只负责模块 ID、版本、依赖和替代声明。入口及迁移资源按约定路径发现，不增加对应配置字段。依赖字段使用 `deps`，替代声明使用 `replaces`。
45: 
46: 身份字段写法：
47: 
48: ```yaml
49: id: github.com/redplum/user
50: version: 1.2.0
51: ```
52: 
53: - `id` 是模块唯一标识，采用 Go 模块路径风格；包含 Go 代码时，与模块根目录 `go.mod` 的 module 路径一致。
54: - `version` 使用 SemVer，YAML 中统一不带 `v`，对应 Git 标签使用 `v1.2.0`；新模块模板初始版本为 `0.1.0`。
55: - 纯前端模块使用相同格式的 ID，不需要为了标识创建 `go.mod`。
56: - 项目内自有模块的 ID 由项目根 `go.mod` 的 module 路径和项目根下的相对目录组成，ID 后缀与项目内目录保持一致；模块目录不要求位于 `modules/` 下，但不能占用工程目录与隐藏目录。例如根路径为 `github.com/acme/shop`、目录为 `modules/order/` 时 ID 为 `github.com/acme/shop/modules/order`，目录为 `order/` 时 ID 为 `github.com/acme/shop/order`。
57: 
58: ### 模块依赖
59: 
60: ```yaml
61: id: github.com/redplum/rbac
62: version: 1.0.0
63: 
64: deps:
65:   github.com/redplum/user: ^1.2.0
66: ```
67: 
68: `deps` 按“模块 ID → 版本约束”声明 Red Plum 模块依赖，支持精确版本与标准 `^` 写法，版本统一不带 `v`。`^1.2.0` 表示 `>=1.2.0 <2.0.0`；零主版本按兼容范围收窄，`^0.2.3` 表示 `>=0.2.3 <0.3.0`，`^0.0.3` 表示 `>=0.0.3 <0.0.4`。Go 依赖由各自模块根层的 `go.mod` 管理，前端包依赖由 `frontend/package.json` 管理，不重复放入 `deps`。
69: 
70: 锁文件固定实际选中的实现及源码提交，以便重现解析结果。
71: 
72: ### 替代声明
73: 
74: ```yaml
75: id: github.com/acme/user
76: version: 2.0.0
77: 
78: replaces:
79:   github.com/redplum/user: 1
80: ```
81: 
82: `replaces` 按“目标模块 ID → 大版本”声明替代关系，不填写目标的次版本、补丁版本或 `^` 范围。上例声明可以替代目标模块的 `1.x` 版本线；替代模块自身版本独立维护，不要求与目标版本一致。
83: 
84: 消费方继续通过 `deps` 声明原目标及其版本约束，不改写成替代实现的 ID。替代维护者负责遵守该目标大版本的约定。
85: 
86: ### 实现唯一性
87: 
88: 同一目标模块在项目中只允许一个实现，不支持原模块与替代模块共存，也不支持同一目标的多版本或多个替代实现共存。
89: 
90: 项目选择替代模块后，所有依赖统一使用该实现。依赖约束无法同时满足时直接报冲突，不通过隔离或并存解决。锁文件保存最终选择。
91: 
92: ### 项目选择替代实现
93: 
94: 项目直接在 `deps` 中引入替代模块，不增加单独的实现选择字段：
95: 
96: ```yaml
97: deps:
98:   github.com/redplum/rbac: ^1.0.0
99:   github.com/acme/user: ^2.0.0
100: ```
101: 
102: 如果 `github.com/acme/user` 声明 `replaces: {github.com/redplum/user: 1}`，解析器就用该实现满足 RBAC 对原用户模块的大版本 1 的依赖，不再安装原实现。替代模块自身版本通过其 `deps` 约束选择；替代目标按 `replaces` 中的大版本匹配。
103: 
104: 发现多个候选实现则报冲突，不按声明顺序或版本高低自动挑选。锁文件记录最终解析结果。
105: 
106: ## 源码与版本锁定
107: 
108: 依赖源码与生成目录由 Git 忽略；项目提交依赖清单和锁文件。锁文件固定实际选中的实现、版本与源码提交，CLI 维护安装结果、工作区和装配输入。
109: 
110: 有锁按锁恢复，无锁解析并生成；`--locked` 拒绝缺锁或与清单不一致，不等同于离线。添加、安装、移除、升级和状态查询的完整行为见[CLI 约定](cli.md#依赖维护redplum)。
111: 
112: 外部依赖目录不保存业务自定义；需要特殊行为时通过模块公开扩展接口，或选择声明替代关系的独立实现。
113: 
114: ## 配置与迁移归属
115: 
116: 模块在 `backend/config.go` 定义配置类型，使用统一加载入口。替代模块沿用目标的组织、配置组名和配置契约，新增专属配置也放同组，见[模块配置](config.md#模块配置)。
117: 
118: 迁移放模块根 `migrations/`。替代实现按自身模块 ID 记录迁移，不继承或映射原模块历史；原模块遗留数据与记录不自动清理，见[数据迁移](migrations.md)。


### docs/design.md
1: # 设计与架构
2: 
3: ## 项目定位
4: 
5: 红梅（Red Plum）是一套面向 Agent 辅助编程的 Go 业务项目模板。它提供可组合的基础能力、统一约定和静态检查边界，让开发集中于业务功能。
6: 
7: 项目包含后端、前端、skill / tool 三部分，独立处理、按需加入。当前 Agent 开发的重点是编程过程中的约束，让开发者和 Agent 从类型、约定与检查结果中获得明确反馈。Agent 文档入口、工具职责和任务流程见下述设计；交付状态见[实现范围](status.md)。
8: 
9: 项目共用一套结构，业务模块按需添加。具体业务模块分别设计，不预先固定全部功能。
10: 
11: ## 设计原则
12: 
13: | 原则 | 约定 |
14: | --- | --- |
15: | 约定优于配置 | 约定路径、入口和资源位置，避免模块重复声明 |
16: | 清晰且简短 | 兼顾语义和链路一致性，在此前提下简化命名 |
17: | 模块独立、按需组合 | 用户业务也是独立模块，前端、后端及资源按需提供 |
18: | 基础集中维护 | 基础模块与公共工具统一维护，使用方按版本升级 |
19: | 静态边界明确 | 类型和现成规则能检查的约束交给工具 |
20: | 减少定制 | 优先依赖原生能力与标准格式，缺口才补小范围适配 |
21: | 先验证再决定 | 关键选型通过实际接入验证，保留能力限制 |
22: 
23: ## 模块如何组合
24: 
25: 每个模块拥有独立的身份、版本、依赖和公开入口。后端通过 Fx 组合构造器与生命周期；前端通过静态可见的入口和完整路由树保留类型关联。
26: 
27: CLI 管理源码、版本、工作区和装配输入，依赖注入负责对象和资源的组合。两者共用模块图，不让业务分别维护脱节的安装与装配步骤。
28: 
29: 自有模块放项目内的模块目录，外部源码放 Git 忽略的 `.redplum/modules/`。项目提交 YAML 清单和锁文件，以便团队与 CI 恢复依赖。自定义行为留在业务模块或独立实现中，外部目录不作为长期修改基础源码的地方。
30: 
31: 替代实现通过 `replaces` 声明目标模块 ID 与大版本，消费方继续依赖目标约定。同一目标只允许一个实现，选择后全项目生效；替代维护者负责遵守约定，框架执行正常编译与边界检查，不另建健全性评估机制。详见[模块与依赖](modules.md)。
32: 
33: ## 业务开发链路
34: 
35: ```text
36: 模块源码与依赖清单
37:     → CLI 安装、解析与装配
38:     → Fx 后端 / 前端入口与路由
39:     → 业务接口与 TSX 页面
40:     → 统一检查、测试与构建
41: ```
42: 
43: API 以 Go 类型及接口注册为来源，经 Huma 生成 OpenAPI，再由 Orval 生成类型、Fetch 调用与 Query 接入。前端各部署形式统一使用 `/api` 相对路径，不手改生成代码。
44: 
45: 成功响应使用业务结构，失败沿用 Huma ErrorModel。列表使用 `page`、`size`，以服务端返回的实际分页值为准；常规编辑采用完整 PUT，区分必填、可空与零值。ID、时间日期和错误状态遵循统一[API 契约](api.md)。
46: 
47: 前端使用 React / TSX 与 Mantine 的有限公共入口。主题、布局语义和静态边界约束风格；Router、Query、Form、Table 分别承担自己的状态职责，日期与错误处理沿用现有组件能力，见[前端开发](frontend.md)。
48: 
49: 强校验针对代码、类型、规范和模块边界，不要求客户端重复执行请求、响应 Schema 校验。服务端输入校验与表单业务校验保留各自职责。
50: 
51: ## 配置与迁移
52: 
53: 模块用 Go 类型声明配置，项目统一生成编辑 Schema、合并公共与环境配置、校验后注入。配置在启动时固定，构建不携带部署配置；HTTP 与配置共用 Huma 校验体系，见[配置](config.md)。
54: 
55: 迁移资源属于模块，执行批次属于项目：所有本次待执行迁移及版本记录在一个事务中统一提交或回滚。并发启动先取得数据库迁移锁，再读取版本与执行；该事务范围不扩展到普通业务操作，见[数据迁移](migrations.md)。
56: 
57: ## 工程入口与交付
58: 
59: ### Agent 文档入口
60: 
61: 项目根 `AGENTS.md` 是 Agent 开发的统一入口，由 `redplum create app` 初次生成，简要说明项目结构、常用 CLI 与项目任务命令、用户模块和 `.redplum/` 生成目录的边界，并留出项目特有规则区。可提示使用用户已安装的 Red Plum Skill，不绑定客户端路径；不复制完整规范。创建后由业务项目维护，后续 CLI 操作、Skill 或官方规范更新均不覆盖。
62: 
63: 具体任务按需提供 Skill，以 `SKILL.md` 描述任务流程，并按需配套脚本和参考资料。官方 Skill 发布包携带该 Skill 实际需要的规范资料，放在 Skill 目录的 `references/` 下并使用包内相对路径；参考资料由独立 Skills 仓库的 `docs/` 生成，同 Skill 使用相同版本。用户自行获取、安装和更新 Skill 包，安装位置遵循所用客户端的约定。
64: 
65: 公开文档站提供 `llms.txt`，作为面向 AI 的文档索引，从文档结构生成并链接详细内容。它承担网站资料导航；项目开发规则由 `AGENTS.md` 承载，任务流程由 Skill 承载。具体自动发现与加载行为取决于所用 Agent 客户端。
66: 
67: ### 开发工具入口
68: 
69: Red Plum CLI 负责从项目模板和模块模板创建项目与模块，并维护项目声明的模块依赖；CLI 将输入填入模板，再执行必要的依赖接入。项目任务脚本提供统一的生成、检查、测试、开发和构建入口，具体命令以目标项目定义为准；任务调用 Red Plum CLI、编译器、静态检查器及测试工具完成工作。
70: 
71: Skill 说明何时使用 CLI 或项目任务入口、如何判断结果并继续工作，不重复实现命令能力。业务运行时供 Agent 调用的工具按业务模块需要单独设计，不预设通用工具集合或统一注册层。
72: 
73: ### 编码 Skill
74: 
75: Red Plum Skills 的统一入口为 `using-redplum`。入口负责阶段选择、任务恢复和交付；每个专业 Skill 的执行步骤、出口和交接以其 `SKILL.md` 为唯一流程定义。本页只说明资源边界，不再复制流程表。
76: 
77: 项目 `AGENTS.md` 应指向已安装的 `using-redplum`，由入口按任务选择专业能力。具体发现、读取或调用机制遵循所用客户端；源码目录不等于客户端安装目录。缺少某项 Skill 时应说明缺失并继续有依据的工作，不伪称已使用。
78: 
79: ### Skill 组织与维护
80: 
81: - Skill 源码在独立 Skills 仓库根的 `<skill-name>/SKILL.md`；名称与目录一致，统一入口为 `using-redplum`，专业 Skill 使用 `redplum-` 前缀。
82: - `description` 用英文描述触发条件，正文与说明用中文。入口组织流程，专业 Skill 定义阶段要求，技术规范按需引用。
83: - 需求、计划与验收分别由 `redplum-requirements`、`redplum-planning`、`redplum-verification` 承担；调研、设计、POC、编码、排障和审查保持各自职责。新增 Skill 应有独立触发场景，补充说明可保留为参考文件。
84: - 规范在本 Skills 仓库的 `docs/` 单点维护；`scripts/sync-references.py` 将规范同步至已有的 `references/`，保证单个 Skill 内的相对链接可用。无需技术规范的 Skill 保持自包含。
85: - 任务流程直接修改对应 `SKILL.md`，不在规范副本重写；新增或修订流程先建立行为对照，再验证阶段选择、产出与交接，检查实际行为，不能只匹配标题。
86: - 项目 `AGENTS.md` 只保留使用入口及项目特有规则，由项目维护。用户独立安装和更新 Skills，Red Plum CLI 不管理、不覆盖它们，`.redplum/` 不保存 Skills。
87: - 源码更新不等于所有客户端已加载；安装后核对实际路径，发现目录可能需要客户端重新扫描。未安装的下游 Skill 不能作为已执行的证据。
88: 
89: ### 任务与发布
90: 
91: 项目通过已有任务入口统一生成、检查、测试、开发和构建；应用使用独立子命令检查配置、迁移和启动服务。构建支持前端嵌入的单二进制与前后端分离形式，详见[CLI 与开发流程](cli.md)和[目录结构](structure.md)。

### docs/cli.md
1: # CLI 与开发流程
2: 
3: 本文是 CLI 命令与流程在整体需求中的原始表述。CLI 的权威需求条目、命令契约与实现都在独立仓库
4: `red-plum-kit/cli`（`docs/requirements.md`、`docs/commands.md`），两侧不一致时以该仓库为准。
5: 
6: ## 依赖维护：redplum
7: 
8: 外部模块源码放 `.redplum/modules/`，自有模块放项目内的模块目录。
9: 
10: | 命令 | 职责 |
11: | --- | --- |
12: | `redplum create app <名称>` | 使用项目模板创建项目，并生成项目根 `AGENTS.md` |
13: | `redplum create mod <模块ID>` | 使用模块模板创建模块并加入当前项目 |
14: | `redplum add <模块ID>[@版本约束]` | 添加依赖或更新已有约束 |
15: | `redplum install [--locked]` | 安装清单声明的全部模块 |
16: | `redplum rm <模块ID>` | 移除直接依赖 |
17: | `redplum up [模块ID]` | 在现有约束内升级指定或全部模块 |
18: | `redplum outdated` | 查询落后版本 |
19: | `redplum list` | 查看实际模块、版本、依赖关系与替代实现 |
20: | `redplum gen` | 生成装配、路由、API 客户端等产物 |
21: | `redplum check` | 检查代码合规、模块规范与安装及生成状态 |
22: 
23: 项目与模块都从对应模板创建；CLI 将名称或模块 ID 填入模板，并完成项目依赖接入。
24: 
25: 官方默认模板随 CLI 同版本发布。创建项目或模块时可以显式指定外部模板仓库，使用该仓库的模板替代本次创建所用的默认模板。
26: 
27: 每个模板仓库根目录承载一种模板，分别遵循[项目结构或独立模块结构](structure.md)。`create app` 使用项目模板，`create mod` 使用模块模板。
28: 
29: 两个创建命令共用 `--template` 参数，短别名为 `-t`，参数位于名称或模块 ID 之后；省略时使用官方默认模板。
30: 
31: ```sh
32: redplum create app shop -m github.com/acme/shop -t <仓库地址>
33: redplum create mod github.com/acme/shop/modules/order -t <仓库地址>
34: ```
35: 
36: `create app` 必须通过 `--module` / `-m` 指定项目的 Go module 路径。`--scope` / `-s` 指定前端包组织名；省略时按模块路径推导。创建只准备模板与模块装配，随后在项目根运行 `redplum install` 安装依赖并生成完整产物。
37: 
38: ```sh
39: redplum create app shop -m github.com/acme/shop -s acme
40: cd shop
41: redplum install
42: ```
43: 
44: 外部模板可通过 `--ref` / `-r` 固定分支、标签或提交；省略时使用仓库默认分支。模板只做文件渲染，不执行仓库脚本。外部模板创建成功后，在标准错误输出仓库、请求 ref 和解析得到的完整提交，默认分支同样保留来源诊断。
45: 
46: `create mod` 接收完整模块 ID，采用 Go module path 格式。项目内模块 ID 必须以项目根 `go.mod` 的 module 路径为前缀，其余路径与项目根下的相对目录一致；模块目录不要求位于 `modules/` 下，但不能占用 `cmd/`、`backend/`、`frontend/`、`config/`、`migrations/`、`scripts/`、`tests/` 等工程目录与隐藏目录。例如项目根路径为 `github.com/acme/shop` 时，`redplum create mod github.com/acme/shop/modules/order` 在 `modules/order/` 创建本地模块，`github.com/acme/shop/order` 则在 `order/` 创建，两种写法都加入项目依赖。默认模块模板包含完整前后端基础文件：`redplum.yaml`、`go.mod`、`backend/module.go`、`backend/order.go`、`frontend/package.json`、`frontend/index.ts` 和 `frontend/order.tsx`；`order` 替换为模块目录名。初始模块版本为 `0.1.0`，项目依赖清单写入 `^0.1.0`。配置定义与 `migrations/` 按需添加。
47: 
48: 项目根 `AGENTS.md` 在项目创建时生成，包含项目结构、常用 CLI 与项目任务命令、用户模块与 `.redplum/` 生成目录边界，以及项目特有规则区。文件归业务项目维护，依赖管理、安装、生成、检查和升级操作均不覆盖它。Skill 与配套规范由用户独立安装和更新，CLI 不管理。
49: 
50: ### 版本与添加
51: 
52: ```sh
53: redplum add github.com/redplum/user@^1.2.0
54: redplum add github.com/redplum/user@1.2.0
55: redplum add github.com/redplum/user
56: ```
57: 
58: 版本使用 SemVer，支持精确版本与标准 `^` 范围，不带 `v`。省略版本时选择最新稳定版，以该版本起始的 `^` 范围写入清单，锁文件固定实际版本。
59: 
60: `up` 只升级到当前约束允许的最新稳定版，不修改约束；省略模块 ID 时升级全部模块。修改约束或跨大版本使用 `add <模块ID>@<新约束>`。所有变更均须满足完整依赖图、替代关系与唯一实现约束。
61: 
62: ### 安装与移除
63: 
64: - 有锁时按锁安装，不主动升级；无锁时解析清单并生成锁文件。
65: - 普通安装保留仍有效的锁定项，仅重新解析清单变更影响的依赖。
66: - `--locked` 在锁缺失或与清单不一致时报错，不修改锁文件；缺失源码仍可按锁定来源下载。
67: - `add`、`rm`、`up` 同步清单、锁文件、受管理源码、工作区与生成装配，清理不再需要的受管理依赖。
68: - `rm` 只移除项目直接声明；仍被间接依赖的模块继续保留。目标没有直接声明时明确提示，不改写其他模块的依赖。
69: - 依赖维护命令不删除项目内的用户模块源码。
70: 
71: ### 查询与结构化输出
72: 
73: `outdated` 只读查询，不修改项目文件：
74: 
75: | 字段 | 含义 |
76: | --- | --- |
77: | `current` | 当前锁定版本 |
78: | `wanted` | 当前约束内最新稳定版 |
79: | `latest` | 最新稳定版，可能超出当前约束 |
80: 
81: `list`、`outdated`、`check` 支持 `--json`。标准输出仅包含一个 JSON 结果，诊断写标准错误。
82: 
83: ### 生成与检查
84: 
85: `gen` 使用当前安装结果生成产物，不隐式升级或安装依赖；源码缺失、安装状态不完整时提示先运行 `redplum install`。
86: 
87: `check` 由 `pnpm check` 调用，检查类型、格式、静态规则、模块边界、迁移约定、受管理源码、锁文件与生成产物一致性。仅检查，不自动修复。
88: 
89: ## 业务项目可执行文件
90: 
91: 以下以项目命令名 `shop` 为例：
92: 
93: | 命令 | 职责 |
94: | --- | --- |
95: | `shop` | 显示帮助，不加载配置或启动服务 |
96: | `shop serve` | 加载、合并、校验配置，执行必要迁移后启动 HTTP |
97: | `shop check` | 仅加载、合并、校验配置 |
98: | `shop migrate` | 执行统一迁移流程后退出，不启动 HTTP |
99: 
100: 需要配置的子命令共用参数，参数位于子命令之后：
101: 
102: | 参数 | 短别名 | 含义 |
103: | --- | --- | --- |
104: | `--env` | `-e` | 指定环境；省略时只读取公共配置 |
105: | `--config` | `-c` | 配置目录，默认当前工作目录的 `./config` |
106: 
107: ```sh
108: ./shop serve -e prod -c /etc/shop
109: ./shop check -e prod -c /etc/shop
110: ./shop migrate -e prod -c /etc/shop
111: ```
112: 
113: 成功返回 `0`，配置、迁移或启动失败返回非零并报告错误。`shop check` 检查运行配置；`redplum check` 检查开发阶段代码与项目状态。
114: 
115: `check` 复用服务的配置加载与校验，不需要先获取数据库连接或监听端口，失败时报告完整配置路径。`migrate` 成功或没有待执行迁移均返回 `0`，配置、锁等待或迁移失败返回非零，结束后释放资源；提前运行 `migrate` 不会让 `serve` 绕过迁移检查，后者按版本账本跳过已完成步骤。详细加载规则见[配置](config.md)，事务、锁与失败处理见[数据迁移](migrations.md)。
116: 
117: ## 项目任务
118: 
119: 项目根 `package.json` 提供统一入口，脚本只转发到 Red Plum CLI：
120: 
121: | 脚本 | 行为 |
122: | --- | --- |
123: | `pnpm dev` | 检查依赖并生成产物，启动后端与 Vite；默认环境 `dev` |
124: | `pnpm gen` | 调用统一生成入口 |
125: | `pnpm check` | 检查代码、模块边界与生成一致性 |
126: | `pnpm test` | 运行必需测试层并校验报告 |
127: | `pnpm build` | 生成、检查并构建单二进制产物 |
128: | `pnpm build:split` | 生成、检查并构建前后端分离产物 |
129: 
130: `redplum app dev --env test` 覆盖开发运行环境；后端代码修改后手动重启。构建不选择运行环境，不携带运行配置。
131: 前端专用脚本另有 `dev:web`、`build:web`、`check:web`、`test:web`、`gen:api`，只覆盖前端一层。
132: 
133: CI 恢复锁定依赖与必要生成产物后，依次执行 `check` → `test` → `build`。脚本负责转发，依赖维护、生成与任务编排集中在 Red Plum CLI，脚本不重复实现这些领域逻辑。
134: 
135: `check` 采用检查模式，不格式化或自动修复，也不能通过覆盖旧产物来掩盖生成不一致。冷启动 CI 先恢复锁定依赖和必要产物，再执行检查；`build` 自身保留检查前置条件。
136: 
137: ## 开发运行
138: 
139: `pnpm dev` 负责统一启动开发环境：
140: 
141: 1. 检查依赖，生成必要的模块装配与其他启动输入。
142: 2. 同时启动 Go 后端和 Vite。
143: 3. 后端代码修改后由开发者手动重启，不提供自动热重载；前端由 Vite 提供 HMR。
144: 4. 用户按 `Ctrl+C` 时统一关闭两个进程；任一进程异常退出时停止另一进程，向任务入口报告失败。
145: 
146: 开发模式不嵌入前端资源，Vite 通过 `/api` 代理到开发后端。不引入后端热重载工具。
147: 
148: ### 开发地址与端口
149: 
150: | 服务 | 默认开发地址 |
151: | --- | --- |
152: | Go 后端 | `127.0.0.1:8080` |
153: | Vite | `127.0.0.1:5173` |
154: 
155: 端口被占用时直接报错，不自动选择其他端口，避免代理目标错位。
156: 
157: 后端监听地址从所选应用配置读取；开发启动入口使用同一地址设置 Vite 的 `/api` 代理，不另行维护一份后端地址。
158: 
159: 发布形式与资源路径见[构建与发布产物](structure.md#构建与发布产物)。


### docs/structure.md
1: # 目录结构
2: 
3: 本页给出业务项目、独立模块与受管理目录的具体文件位置。模块身份及替代见[模块与依赖](modules.md)，运行步骤见[CLI 约定](cli.md)。
4: 
5: ## 项目结构
6: 
7: ```text
8: shop/
9: ├── AGENTS.md                     # Agent 开发入口，项目命令与项目特有规则
10: ├── go.mod                        # 项目根 Go 模块
11: ├── go.sum
12: ├── redplum.yaml                   # 项目依赖清单
13: ├── redplum.lock                   # 实际解析版本与依赖锁定结果
14: ├── go.work                        # CLI 维护的 Go 工作区
15: ├── package.json                   # workspace 根、统一任务入口与生成代码运行依赖
16: ├── pnpm-lock.yaml
17: ├── pnpm-workspace.yaml
18: ├── .gitignore
19: ├── cmd/
20: │   └── shop/                     # 根据项目命令名生成，不固定叫 app
21: │       ├── main.go               # CLI 入口与退出处理
22: │       └── bootstrap.go          # 应用装配与启动，与 main.go 同包
23: ├── backend/                      # 项目后端模块
24: │   ├── module.go                 # Fx 装配入口
25: │   └── config.go                 # 项目配置定义（按需）
26: ├── frontend/                     # 项目前端应用
27: │   ├── package.json              # 应用依赖与前端脚本
28: │   ├── index.html                # HTML 入口
29: │   ├── main.tsx                  # React 挂载入口
30: │   ├── index.ts                  # 模块公开入口
31: │   ├── router.tsx                # 项目路由组合
32: │   ├── vite.config.ts
33: │   ├── tsconfig.json             # 类型检查配置入口
34: │   ├── tsconfig.app.json         # 浏览器代码
35: │   └── tsconfig.node.json        # Node 工具配置
36: ├── migrations/                   # 项目自身模块的迁移资源（按需）
37: │   ├── embed.go                  # 嵌入并导出迁移 SQL
38: │   └── 0.1.0.sql                 # 版本迁移示例
39: ├── modules/                      # 用户维护的业务模块示例（ID 后缀即模块目录）
40: │   └── order/
41: │       ├── redplum.yaml
42: │       ├── go.mod
43: │       ├── go.sum
44: │       ├── backend/
45: │       │   ├── module.go          # 后端 Fx 模块入口
46: │       │   ├── config.go          # 模块配置定义（按需）
47: │       │   └── order.go
48: │       ├── frontend/
49: │       │   ├── package.json       # 模块前端依赖
50: │       │   ├── index.ts           # 前端公开入口
51: │       │   └── order.tsx
52: │       └── migrations/
53: │           ├── embed.go
54: │           └── 0.1.0.sql
55: ├── config/
56: │   ├── app.toml                   # 始终读取的公共配置
57: │   ├── app.dev.toml               # 开发环境配置
58: │   ├── app.test.toml              # 测试环境配置
59: │   └── app.prod.toml              # 生产环境配置
60: └── .redplum/                      # CLI 管理，Git 忽略，可恢复
61:     ├── modules/                   # 拉取的外部依赖模块源码
62:     │   └── github.com/
63:     │       └── redplum/
64:     │           └── user/          # 外部用户模块源码
65:     ├── config/
66:     │   └── app.schema.json        # 配置编辑提示与检查约束
67:     ├── backend/
68:     │   ├── modules.go             # 后端模块导入与 Fx 组合
69:     │   └── assets/                # 单二进制模式生成
70:     │       ├── embed.go           # 嵌入并导出前端资源
71:     │       └── web/               # 前端构建输出
72:     ├── frontend/
73:     │   ├── modules.ts             # 前端模块入口汇总
74:     │   ├── routes.ts              # 路由装配导出
75:     │   ├── providers.tsx          # 模块默认 Provider 装配
76:     │   └── api.ts                 # Orval 生成的 Fetch、类型与 Query 接入
77:     └── openapi.json               # 后端导出的 OpenAPI
78: ```
79: 
80: `cmd/<项目命令名>/` 是后端启动层。项目根包含 `go.mod`、`go.sum`，不为命令目录单独创建 Go module。项目内的模块目录保存用户自有模块，ID 后缀与该目录一致；示例放在 `modules/` 下，也可以直接放在项目根。`.redplum/modules/` 保存受管理的外部源码，用户不在其中维护业务修改。模板只产出一套结构；没有前端的项目不生成前端文件。
81: 
82: `go.work` 由 CLI 更新，自有模块通过 `use` 纳入，受管理外部目标通过生成的本地映射接入；生成包共用根模块，不独立列为工作区模块。用户无需手工维护 `replace`。模块 ID 到 `.redplum/modules/` 路径的映射由 CLI 统一处理，图中的域名路径仅展示一个依赖实例。
83: 
84: ## 模块结构
85: 
86: `redplum create mod` 从模块模板创建模块描述、Go module、后端 Fx 入口与业务文件，以及前端包描述、公开入口与业务组件。`backend/config.go` 和 `migrations/` 按需创建。
87: 
88: ```text
89: order/
90: ├── redplum.yaml        # 模块描述
91: ├── go.mod             # 位于模块根目录（默认生成）
92: ├── go.sum             # Go 依赖校验和
93: ├── backend/
94: │   ├── module.go       # Fx 入口（默认生成）
95: │   ├── config.go       # 配置类型、默认值与约束（按需）
96: │   └── order.go        # 后端业务实现（默认生成）
97: ├── frontend/
98: │   ├── package.json    # 模块前端依赖（默认生成）
99: │   ├── index.ts        # 前端公开入口（默认生成）
100: │   └── order.tsx       # 前端业务实现（默认生成）
101: └── migrations/         # 模块根层的迁移资源
102:     ├── embed.go        # 嵌入并导出迁移资源
103:     └── 0.1.0.sql       # 版本迁移示例
104: ```
105: 
106: `go.mod` 位于模块根目录，使 `backend` 和 `migrations` 同属一个 Go module。`migrations/embed.go` 在资源所在目录嵌入 SQL，后端通过导入迁移包获取资源，无需跨父目录嵌入。
107: 
108: `frontend/package.json` 声明模块前端依赖，由项目 pnpm workspace 统一安装；`pnpm-lock.yaml` 统一位于项目根目录，模块内不另建锁文件。
109: 
110: 模块功能可以只实现一侧；`create mod` 的默认模板同时生成前后端基础入口。纯前端模块不需要 Go 工程文件。模块描述不重复声明约定入口 `backend/module.go`、`frontend/index.ts` 及资源目录。
111: 
112: 迁移资源由模块自己维护，项目统一发现和执行，不要求额外复制到项目根。迁移目录的“根层”指模块根层。一次迁移批次覆盖所有模块的待执行迁移，统一使用项目级数据库事务。
113: 
114: ## 主入口与工作区
115: 
116: 后端入口位于 `cmd/<项目命令名>/main.go`，同目录 `bootstrap.go` 负责应用装配与启动，两者属于同一个 `main` 包。创建项目时根据项目名生成命令目录；`app` 不是固定目录名。
117: 
118: 例如项目命令名为 `shop`，从根目录执行 `go run ./cmd/shop`，构建可执行文件默认名为 `shop`。
119: 
120: 前端以 `frontend/` 为 Vite root，`frontend/index.html` 引用 `/main.tsx`，由 `frontend/main.tsx` 挂载 React。根脚本通过切换到 `frontend/` 运行前端命令，使 Vite 自动发现同目录配置。
121: 
122: `frontend/index.ts` 只提供模块公开导出，不执行挂载，也不反向引用项目启动入口。浏览器代码和 Node 配置分别由 `tsconfig.app.json`、`tsconfig.node.json` 检查，`tsconfig.json` 为配置入口；检查范围须覆盖参与装配的模块和生成代码，而不只包含主入口的导入闭包。
123: 
124: 根 `package.json` 负责统一脚本、工具版本约束，以及根层生成代码直接引用的运行依赖（当前为 React 与 TanStack Query），`frontend/package.json` 声明应用依赖，各模块仍声明自身依赖。workspace 显式纳入各模块的前端包与 `.redplum/modules/` 下的前端包，统一使用根锁文件。
125: 
126: 前端 workspace 包名与 Go 模块 ID 分开：项目应用包使用 `@<组织>/app`，模块前端包使用 `@<组织>/<模块名>`，模块包名不附加所属项目名。应用包和模块包均设为 `private: true`。例如组织为 `acme` 时，项目应用包名为 `@acme/app`，`order` 模块包名为 `@acme/order`。根 `package.json` 是 workspace 根层工具包，不与应用或模块前端包共用身份。
127: 
128: `.redplum/frontend/` 生成代码引用解析后的模块公开入口静态路径；不假定它会继承 `frontend/package.json` 的包解析环境。Orval 生成的 `api.ts` 直接导入 TanStack Query，因此其运行依赖由根 `package.json` 显式声明；应用和模块仍声明自身使用的依赖，不靠 hoist 或应用目录为生成代码兜底。
129: 
130: 自动生成文件归入 `.redplum/`，不手工修改。隐藏目录可以通过完整包路径显式导入；生成包共用根目录 `go.mod`，不额外创建生成模块。外部依赖模块保留各自的 `go.mod`。
131: 
132: ## 受管理目录
133: 
134: 项目内的模块目录为自有模块，`.redplum/modules/` 为 CLI 管理的外部依赖。`.redplum/` 整体由 Git 忽略，依赖按根层锁文件重新拉取，生成代码重新生成。锁文件、用户配置和迁移执行状态不放入该目录。
135: 
136: 生成层的 `backend/`、`frontend/` 按启用部分生成。生成前准备依赖，构建和检查前确保生成结果完整，移除模块时清理旧产物。隐藏生成包须由统一检查入口显式覆盖，不能只依靠根层 `go test ./...`。
137: 
138: ## 构建与发布产物
139: 
140: 同一套业务代码支持两种构建模式，默认单二进制，按需选择前后端分离模式。模式由 `pnpm build` 与 `pnpm build:split` 选择，CLI 的 `--mode` 只接受 `single`、`split`，默认 `single`，其他值直接报错。
141: 
142: | 模式 | 发布产物（以项目命令名 `shop` 为例） | 行为 |
143: | --- | --- | --- |
144: | 单二进制（默认） | `dist/shop` | 先构建前端，再通过 `go:embed` 嵌入静态资源，由后端提供资源与 API |
145: | 前后端分离 | `dist/backend/shop`、`dist/frontend/` | 后端提供 API，前端静态资源独立部署 |
146: 
147: `dist/` 用于发布产物，由 Git 忽略；`.redplum/` 继续用于受管理依赖和生成代码。两种模式共用业务实现。
148: 
149: ### 构建模式参数
150: 
151: ```sh
152: pnpm build              # 默认单二进制，等同 --mode single
153: pnpm build:split        # 前后端分离
154: ```
155: 
156: `--mode` 是 CLI 构建参数，不是应用运行环境，不用于选择 `config/app.<环境>.toml`。非法值在执行构建步骤前报错，不静默回退。
157: 
158: ### 前端嵌入资源
159: 
160: ```text
161: .redplum/backend/assets/
162: ├── embed.go
163: └── web/             # 前端构建输出
164: ```
165: 
166: 单二进制构建时，先将前端构建到 `.redplum/backend/assets/web/`，再编译 Go。`embed.go` 在同一包内通过 `go:embed` 嵌入并导出 `web/` 资源，由后端提供静态资源与 SPA 回退。
167: 
168: 分离模式不引入该嵌入包，前端直接输出到 `dist/frontend/`。构建流程应保证模式切换时不会误引入上次生成的嵌入资源。清理构建产物时保留 `.redplum/modules/` 中的依赖源码。
169: 
170: 中间资源由 CLI 管理，保留在 `.redplum/`；最终发布产物仍在 `dist/`。
171: 
172: ### API 路径与转发
173: 
174: 前端统一使用 `/api` 相对路径调用后端，各环境共享同一套业务调用代码。
175: 
176: | 场景 | 请求处理 |
177: | --- | --- |
178: | 开发 | Vite 将 `/api` 请求代理到开发后端 |
179: | 单二进制部署 | 后端在同一来源提供前端静态资源和 `/api` 接口 |
180: | 前后端分离部署 | 部署侧反向代理将同一来源下的 `/api` 请求转发到后端，静态资源由前端部署提供 |
181: 
182: 分离部署采用同源入口，不要求业务代码切换 API 域名。具体代理地址由开发或部署配置负责，不硬编码在业务模块中。
183: 
184: ### SPA 路由回退
185: 
186: 访问前端页面路径或直接刷新该路径时，返回 `index.html`，由前端路由处理页面匹配。`/api` 及其子路径不参与页面回退；找不到的静态资源保留真实错误，不以 HTML 页面响应掩盖资源缺失。
187: 
188: 单二进制部署由后端处理上述规则；分离部署由静态服务器或部署侧代理处理。
189: 
190: 配置文件及其加载规则见[配置](config.md)，迁移文件及事务规则见[数据迁移](migrations.md)。
